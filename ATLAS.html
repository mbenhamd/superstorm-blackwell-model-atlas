START_HERE.md

Start here: a model-serving factory

You do not need to know GPU programming to navigate this repository. The core distinction is the model is the trained machine; the engine operates it; the platform keeps the service available.

One request, from question to answer

A tokenizer turns text into numbered pieces called tokens. An embedding turns each number into a vector, a list of numerical features. The model repeatedly transforms those features through its layers. Attention retrieves useful information from earlier tokens. A feed-forward block performs another learned transformation. A final head produces scores for possible next tokens, and the sampler chooses a token. This repeats until a stopping condition is met. Images require an additional encoder and preprocessing path. The exact implementation varies across the eight model reports. qwen3.8-27b-CARD gemma-4-31b-it-CFG mistral-medium-3.5-CFG

Prefill is reading the question and existing conversation. Decode is writing the answer a piece at a time. A restaurant analogy helps: preparing all ingredients is not the same job as plating each course. An optimization that speeds preparation might slow service if it monopolizes the same kitchen.

Dense versus mixture of experts

A dense model uses its ordinary feed-forward blocks for every token. An MoE model routes tokens through a selected subset of experts. A building with 896 specialist offices may consult only 16 offices for a token, but the others still occupy floor space. Activated parameters describe selected work; total resident parameters and tensor bytes describe weight storage. Do not buy GPU memory based only on the activated count. kimi-k3-CARD glm-5.3-flash-CARD

Four kinds of memory

Weights are the learned constants. KV cache stores attention information associated with previous tokens. Recurrent state is the running summary used by linear-attention blocks. Temporary memory includes activations, graph capture, communication buffers, quantization/repacking workspaces and speculative verification. A model can fit its weights and still fail to start or run long requests.

A notebook is a useful analogy for recurrent state, but it is not a lossless transcript. Full-attention or sparse-history layers remain important. Conversely, a small recurrent state can need several snapshots per request for prefix caching, overlap and speculative rollback. The per-sequence state matrix alone is not the complete state-pool allocation. qwen3.8-27b-GR kimi-k3-GR glm-5.3-flash-GR

What precision changes

BF16 uses 16 bits per represented element. FP8 usually uses eight. NVFP4 and MXFP4 use four-bit values plus different scaling structures. Think of recording measurements to different precision, with scale notes attached to groups of values. They are not interchangeable file extensions. Exported checkpoints frequently mix several precisions. NV4 TE CUDNN

What the evidence labels mean

Publisher fact means that a primary source states it. Config extraction means the value is present in the cited machine-readable configuration. Source inspected means particular code ranges were read at a named commit. Publisher benchmark means the author measured it under stated conditions. Derived means a calculation here uses explicit assumptions. Candidate means a setting needs testing. Not verified means no confirmation was obtained; it does not mean false.

There is no defensible universal winner yet

A useful comparison fixes the task distribution, prompt/output lengths, quality threshold, reasoning settings and latency objective. Compare per-node goodput for capacity planning and per-request latency for interactivity. Do not rank engines by unrelated benchmark rows from B200, GB300, RTX Blackwell and an unspecified B300 OEM node.

Choose a starting engine using evidence of the exact checkpoint path and the team’s operational constraints. Promote a candidate only after correctness and workload tests. vLLM and SGLang can both be benchmarked without changing the KServe lifecycle design for a basic single-node service; advanced disaggregation and routing require engine-specific integrations. Suggested workload portfolios

For short interactive chat, prioritize first-content latency and stable output pacing; include target-only baselines because drafting is not free. For coding agents, preserve multi-turn reasoning/tool serialization and measure actual draft acceptance. For long documents, constrain context and concurrency explicitly and measure retrieval quality. For multimodal tasks, include image preprocessing/encoder time and enforce input limits. For high-volume endpoints, compare independent small-model replicas against wider TP groups at equal node occupancy.

Hardware target: eight B300 GPUs per node

Verified hardware facts versus supplied inventory

NVIDIA’s specifications, rechecked October 15, 2026 UTC, list a DGX B300 with eight B300 GPUs, 288 GB per GPU and approximately 2.3 TB aggregate GPU memory. Its CUDA GPU table identifies B300 as compute capability 10.3. Those are architectural references; the supplied SXM6-AC label does not identify a complete DGX-equivalent bill of materials. CPU, RAM, NVMe, NICs, firmware, power and cooling remain OEM-specific until inventoried. HW CC

Eight times 288 is 2,304 advertised GB. If those units are interpreted as decimal bytes, that is approximately 2,145.77 GiB. Treat this as a unit-conversion illustration, not a prediction of nvidia-smi output: query the memory actually exposed by the driver and allocator. Neither advertised total nor driver-visible total is all available for weights.

Preflight before tuning

Run python scripts/preflight.py --output preflight.json on the actual inference host. It runs read-only version and topology queries; it does not set GPU clocks, power limits, MIG mode, network devices or kernel parameters. Confirm eight intended devices, compute capability, driver/CUDA compatibility, peer-access topology and process exclusivity. Record CPU architecture so x86_64 B300 and Grace-based GB300 software images are not confused.

Do not treat a workstation RTX Blackwell measurement as an HGX B300 measurement. SM12x devices, B300 SM10.3, and B200 SM10.0 have different kernel and topology requirements. Likewise, GB300’s host and memory architecture is not an automatic match for an x86 SXM node. CC qwen3.8-27b-GR deepseek-v4-flash-0731-VR

Blackwell-specific optimization order

First establish an image that loads the correct artifact with finite, coherent outputs. Next verify kernel selection and mixed-format behavior. Only then compare FP8 versus NVFP4, attention backends, CUDA graph modes, batch caps, cache precision and speculative decoding. Inspect whether time is spent in expert GEMMs, attention, routing, all-to-all, reductions, host scheduling, tokenization or memory movement. For low-concurrency dense models, launch and synchronization overhead can dominate; at longer contexts, cache bandwidth can dominate. This is a workload hypothesis to test with traces.

Scale overhead

For an ideal one-dimensional payload, MXFP4 with one byte of scale per 32 four-bit values consumes 0.5 + 1/32 = 0.53125 bytes per value. NVFP4 with one byte per 16 values consumes 0.5625 bytes per value before the outer tensor scale. These correspond to 4.25 and 4.5 effective bits for those parts. Real exports can add padding, layouts and mixed modules. The Transformer Engine training recipe also describes 16×16 weight scaling; the one-dimensional estimate here must not be applied to every NVFP4 recipe. NV4 TE4 CUDNN

For Qwen Flash Next, the approximately 51B n-gram table is FP8 in the NVIDIA derivative, so its ideal value payload is around 51 GB before scales and padding. Four-bit estimates that omit that table are incomplete. qwen3.8-flash-next-NV

Uniform GQA cache

For an unpadded, non-shared cache with separate K and V:

KV bytes = 2 × layers × KV_heads × head_dim
           × tokens_per_sequence × concurrent_sequences × bytes_per_element

Use it only where those assumptions hold. At 262,144 tokens and one sequence, Mistral’s 2 × 88 × 8 × 128 × 262144 × 2 gives 88 GiB. Qwen 27B’s 2 × 16 × 4 × 256 × 262144 × 2 gives 16 GiB for its full-attention layers, plus separate linear state. These are aggregate, unsharded BF16 payloads; the engine determines per-rank allocation and any replication. A factor-of-two precision change affects element payload, not necessarily every allocation. mistral-medium-3.5-CFG qwen3.8-27b-CFG

Do not apply this formula unchanged to Kimi MLA, DeepSeek compressed attention, GLM sparse indexers or Gemma’s heterogeneous local/global and key/value-sharing behavior. A head count in config is not an allocator specification. kimi-k3-CFG deepseek-v4-flash-0731-CFG gemma-4-31b-it-CFG

Practical capacity workflow

Measure post-load free memory, graph-capture peak, KV token capacity, state-slot capacity and maximum running requests separately. Increase request length with batch fixed, then batch with length fixed. Repeat after changing speculation, cache dtype or multimodal input shape. Four layers of compatibility

Numeric format: bit layout, scale data types and granularity. Serialized representation: tensor names, packed shapes, exclusions, exporter metadata. Mathematical operator: activation, bias, normalization, router weighting, clamping and residual behavior. Runtime implementation: supported kernel, alignment, repacking, sharding and target GPU architecture.

A failure at any layer can break the result. In the inspected SGLang code, FP4 GEMM selects different W4A4 and W4A16 paths and checks whether FlashInfer functionality is available. Padding rules differ across kernel families. In the Kimi fixes, correct scale loading and SiTU activation behavior are as important as selecting four-bit matrix multiplication. GQUANT KIMIPR KIMIVPR

FP8 KV is independent

Weight precision changes model operations. KV precision changes stored attention history. Recurrent-state precision changes an additional state representation. Test these separately: baseline weights + baseline cache; low-precision weights + unchanged cache; then lower-precision cache/state. Otherwise an accuracy difference cannot be assigned to its cause.

The SGLang Qwen recipe gives a concrete metadata trap: some derivative exports default auto KV to FP8, whereas NVIDIA’s export leaves it BF16 without an explicit setting. Matching command text with auto therefore does not necessarily match effective precision. qwen3.8-27b-GR

Why four-bit can win, and why it can lose

A lower-byte representation may reduce weight bandwidth and let a larger useful batch or cache fit. It can also introduce scale handling, conversion, padding, calibration error and backend constraints. At low concurrency, synchronization and launch overhead may dominate the saved arithmetic. At long context, attention-history traffic can dominate expert weights. These are reasons to measure, not reasons to reject quantization.

benchmarks/PROTOCOL.md

Benchmark and correctness protocol

Define the decision before measuring

Choose a service-level objective and quality threshold. For example, compare request goodput while meeting a declared p95 first-token and generation-latency budget. Do not replace those budgets with convenient measured numbers after a run. Store the exact values in each experiment manifest; this atlas supplies no invented production SLA.

Compare engines on the same node, model revision, export, tokenizer, chat template, thinking mode, sampling, input/output lengths, concurrency, arrival process and cache state. A warm prefix hit against a cold-cache run is not a fair comparison. Weight precision, KV precision and recurrent-state precision must be recorded separately. Cap vision payloads and account for visual tokens rather than pretending an image is one text token.

Correctness gates before speed

First test target-only loading and finite outputs against the publisher/reference implementation. Cover ordinary chat, arithmetic, coding, multilingual requests, EOS/stop handling, JSON schemas, tool-call boundaries and image inputs where supported. Quantized checkpoints require a representative held-out quality evaluation, not only one coherent answer. Compare aggregate metrics and failure categories, not exact sampled strings.

Then test long contexts, repeated prefixes, cache eviction, cancellation, graph replay, batch size changes and partial failures. Hybrid models must preserve recurrent and convolutional state as well as token KV. For speculative decoding, verify that accepted and rejected branches commit or restore the right state. Use native acceptance; reject simulated-acceptance environment settings. Evaluate the same workloads with speculation disabled.

For 0731 DeepSeek use its encoding and DSpark contract, not a preview model's MTP invocation. For Kimi match the drafter to the engine and target. For Qwen Flash Next include PLE/ngram and draft tensors in load accounting. For Gemma verify no unsupported audio feature was accidentally enabled from a generic example.

Minimum experiment matrix

Run target-only first. Sweep input lengths 4K, 16K, 32K and 64K; extend to 128K and the native maximum only after capacity and accuracy gates pass. Sweep output lengths representative of the application, such as 128 and 1,024 tokens, plus the real trace. Include concurrency 1, 8, 32 and the point just before saturation. Repeat independent runs, randomize order and retain failures.

For dense Qwen/Gemma compare TP1 replicas with TP2/4 as total-node capacity, not only one process's throughput. For large MoE compare the documented TP/DP/EP topologies before introducing cross-node communication. For hybrid models sweep the state/KV pool split only with measured pool demand. For DSpark/MTP record acceptance, verification work and queueing at each load, not a single best batch-one speedup.

Metric definitions

TTFT is time from request submission to first generated semantic content. State whether reasoning or tool deltas count. First-answer latency excludes hidden/reasoning content and may be much larger. End-to-end latency includes the complete response. ITL requires reliable per-token emission timing: an SSE chunk can contain zero or several tokens, so chunk gaps are not automatically token latency.

TPOT is generation time per output token under an explicitly stated formula. A network-based approximation from first content to final event divided by completion_tokens−1 is a proxy, not a GPU-only measurement. Output throughput uses the total reported output-token count divided by full measurement wall time. Goodput counts only successful requests/tokens meeting the declared latency and quality objective. Report error rate, p50/p95/p99 and offered load; never drop failures from the denominator silently.

Natural acceptance is observed accepted draft work under the deployed sampling procedure. Define whether the length includes the extra target token. Memory includes resident weights, caches, recurrent state, graph capture, activations, workspaces and communication buffers. Keep physical/advertised GB and binary GiB explicit.

Included runner and its boundaries

run_streaming.py provides a lightweight, closed-loop, concurrent HTTP/SSE probe using the Python standard library. It records semantic deltas and usage when the endpoint supplies it. It does not infer tokens from chunk counts, execute returned tools/code, generate large synthetic prompts or supply an open-loop arrival process. Use the pinned engine's native benchmark harness for controlled token workloads and detailed kernel/service measurements, and compare against this client view.

The probe accepts one completion per request (n=1) and requires a completed choice with a recognized finish reason. [DONE] alone cannot mark an empty or truncated stream successful. Tool-call identifiers and indices alone do not count as first semantic output; function names and argument text do. ok measures protocol completion, not answer quality or SLO compliance. A missing usage count stays unknown, and any failed request or missing count suppresses total output-token throughput. Both an origin URL and an API base ending in /v1 are accepted. The timeout applies to socket operations and is checked between bounded line reads, so it is not strict wall-clock cancellation.

GLOSSARY.md

Glossary: meaning, purpose and analogy

Use the analogies to build intuition, not as exact mathematics. Architecture-specific terms link back to the company reports; numeric and kernel claims are sourced in the evidence register, precision report and framework reviews. Unverified expansions are explicitly left as project/configuration names.

Token

Tokenizer unit. A piece of text or a model-specific input symbol, not necessarily a word.

Analogy: A page is cut into differently sized tiles; count tiles, not words.

Tokenizer / chat template

Text encoding and conversation serialization. Convert content and roles into the exact IDs/boundaries the model learned. Wrong tool/reasoning boundaries can break an otherwise fluent endpoint.

Analogy: The same message written in the wrong envelope format reaches the wrong desk.

Parameter / weight

Learned numerical value. Total weights drive storage; active weights approximate work per token only under stated accounting.

Analogy: All books on the shelves versus the books consulted for one question.

Dense

All ordinary feed-forward layers participate. No expert router chooses a small subset of the model’s MLPs per token.

Analogy: One permanent team reviews every paragraph.

MLP / FFN

Multilayer perceptron / feed-forward network. The transformations within a decoder block after or alongside attention; can be dense or replaced by experts.

Analogy: An editing workshop transforms what the reader has gathered.

MoE

Mixture of Experts. A router chooses a small number of expert networks per token. All experts still need storage somewhere unless deliberately offloaded.

Analogy: A large hospital employs many specialists; only a few see one patient.

Top-k routing

Select k routed experts. The number of selected experts is not the number resident in memory. Shared experts can add work beyond routed top-k.

Analogy: Two assigned specialists plus the general practitioner still count as three workers.

Shared expert

Always-used expert branch in the relevant architecture. Distinguish always-on shared computation from token-selected routed experts.

Analogy: A common reception desk supports every specialist appointment.

Latent MoE

Experts operating through a reduced representation. Kimi projects into a smaller expert space and back. Layer dimensions and kernels must match that interface.

Analogy: Specialists exchange compact forms rather than the entire case folder.

Attention

Context-dependent information lookup. Query/key comparisons determine how values contribute to a token’s representation.

Analogy: A reader searches previous notes before choosing the next sentence.

MHA / GQA / MQA

Multi-head / grouped-query / multi-query attention. Query heads can share key/value heads, reducing cached K/V. Always read explicit dimensions.

Analogy: Several readers share fewer reference notebooks.

KV cache

Key/value cache. Saved attention data avoids recalculating past token projections. It grows with context in ordinary full attention.

Analogy: Keep the reference notes instead of rereading the entire source every time.

MLA

Multi-head Latent Attention. A model-specific compressed latent representation changes projection and cache layout. Ordinary GQA memory arithmetic is not a full MLA estimate.

Analogy: Compress the reference folder before storing it, then reconstruct what is needed.

DSA

DeepSeek Sparse Attention. An indexed selection mechanism reduces which past representations receive expensive attention. Index and selected-value caches are distinct.

Analogy: A catalog points to relevant shelves rather than scanning every book.

QSA

Qwen sparse-attention path. Qwen’s particular sparse/indexed attention implementation must be read with its own compression and index shapes.

Analogy: A different library uses a different catalog; shelf numbers are not interchangeable.

SWA

Sliding-window attention. Restricts a layer’s direct attention to a recent window; some architectures interleave global layers.

Analogy: Keep recent pages on the desk, occasionally consult the complete archive.

NoPE

No positional encoding in the named path. A specific attention path omits ordinary positional encoding; not a claim the whole model has no ordering information.

Analogy: One index sorts by content, while other mechanisms preserve sequence.

RoPE

Rotary position embedding. Transforms components according to position. Partial rotary dimensions can differ from total head size.

Analogy: Position stamps help distinguish otherwise similar entries.

YaRN

A RoPE context-extension method. Its configured scale/original window affects position handling; a larger limit alone does not guarantee useful long-context accuracy.

Analogy: Stretch the map’s coordinate scale, then check that landmarks still line up.

KDA

Kimi Delta Attention. A gated recurrent/linear-attention mechanism with its own state and convolution path. It cannot be treated as ordinary token KV alone.

Analogy: Maintain and revise a compact notebook as each sentence arrives.

GDN

Gated DeltaNet. A gated delta-rule recurrent attention family used in Qwen hybrids; its state dimension and cache slots affect concurrency.

Analogy: The notebook has rules for what to replace, retain or forget.

SSM / recurrent state

State-space model / persistent running representation. Serving terminology may group recurrent caches under SSM/Mamba labels even for different linear-attention architectures.

Analogy: A running summary survives between steps; copying it also consumes space.

Convolution state

Short recent-input history. Hybrid blocks may require convolution buffers as well as matrix state. Disaggregation and rollback must preserve both.

Analogy: The running summary also carries a small stack of the latest pages.

mHC

Qwen 3.8 27B: architecture

Data flow

Vision/text → [GDN → GDN → GDN → gated full attention] × 16, with dense MLPs → output head; optional MTP.

How the parts work together

Three Gated DeltaNet layers are followed by a gated full-attention layer, repeated through the text backbone. The linear-attention path maintains a recurrent matrix state with a short convolutional component. Full-attention layers retain ordinary token-history cache. Consequently, the model has both a context-dependent cache and a concurrency-dependent state pool.

The key and value head counts in the linear path differ. The full-attention path has its own query-head count, KV-head count and head dimension. Deriving head dimensions by dividing hidden width by a familiar head count would produce the wrong shapes here; use the explicit configuration.

The feed-forward network is dense, not MoE. Every token traverses those linears; there is no expert-parallel switch that turns it into a sparsely activated 27B model. The vision encoder is shared infrastructure for image/video inputs, with spatial merging and temporal patching before language processing.

MTP is an optional additional serving path. It changes scheduling and temporary-state needs, not the base model’s dense-versus-MoE identity. The official context extension beyond the native window is not evidence that every engine, quantization and workload preserves useful accuracy at that length.

Engine and topology

Begin with vLLM TP1 BF16 at 32K context, then the same FP8 and NVFP4 workload. Repeat with SGLang TP1. Keep vision enabled for multimodal validation and explicitly constrain its allowed input sizes; a text-only optimization must be a separate profile.

Qwen 3.8 Flash Next: architecture

Data flow

Text/image/video inputs → vision processing where needed + token embeddings → 12 groups of three GDN/MoE layers and one QSA/MoE layer → output. Gated residual branches span the backbone; n-gram/PLE features enter at its second layer. MTP adds an optional serving path.

How the parts work together

The backbone combines three recurrent Gated DeltaNet layers with a sparse-attention layer in each four-layer group. Qwen describes a selection budget of 512 four-token micro-blocks, or 2,048 tokens. That budget limits selected attention history; it is not the model's context limit or a complete cache-size formula. The output remains autoregressive.

A large n-gram embedding table provides an additional lookup path for local token patterns. It changes the balance between arithmetic and table access. The PLE configuration identifies where that representation is injected; treating it as an ordinary vocabulary embedding or dropping it because it is not in the 125B headline would change the model.

The main MoE selects ten routed experts plus one shared expert. Alongside it, the publisher describes four residual branches with data-dependent read gates and per-branch write gates. The configuration field hc_count alone does not establish equivalence to another model family's hyper-connection mechanism.

When MTP is enabled, its loader must respect its own expert precision, which differs from the main routed experts in NVIDIA's export. A target-only load cannot establish that this speculative path works.

Gemma 4 31B IT: architecture

Data flow

Vision/text → [five local sliding layers → one global layer] ×10 with dense MLPs → tied output head + logit soft-cap → sampling.

How the parts work together

Five local sliding-attention layers are followed by one global layer. Local attention keeps recent context within a bounded window, while global layers provide long-distance interaction. This substantially changes the cache shape relative to 60 uniform full-attention layers.

Local and global attention have different KV-head counts and head dimensions. The publisher describes unified keys and values in the global layers. This same-layer behavior is distinct from the configuration’s num_kv_shared_layers: 0. A formula that allocates separate K and V buffers in every layer is therefore an assumption about storage, not a deduction from the config. Inspect the selected engine’s allocator before claiming an exact physical cache size.

The feed-forward blocks are dense and use the configured GELU approximation. Tied embeddings and output-head behavior matter both for loading and for quantization exclusions. Final logit soft-capping changes how scores reach the sampler; it must remain in the generation path.

Image features are processed through the vision tower before text generation. The presence of audio token identifiers elsewhere in a shared family configuration is not proof of an audio encoder in this specific variant. Capability must be checked at the concrete model, processor and runtime level.

Kimi K3: architecture

Data flow

Text / vision features → KDA or gated MLA → attention-residual mixing → dense or latent MoE → repeat → output head; optional DSpark proposes → target verifies → commit accepted state.

How the parts work together

The text backbone alternates frequent Kimi Delta Attention (KDA) updates with periodic gated multi-head latent attention (MLA). KDA carries a recurrent summary forward; the MLA layers retain access to token history through compressed attention representations. This combination makes the model neither ordinary full attention everywhere nor a constant-memory model everywhere. A long conversation still consumes token-cache memory in the MLA layers.

The feed-forward path is a latent mixture of experts. Routing selects specialists, but the specialist computation is represented in a narrower latent space rather than treating every expert as a full-width dense feed-forward network. The dense prefix, shared experts, routers, normalization, and residual machinery still perform work. The number of selected experts therefore does not by itself determine end-to-end FLOPs or latency.

The configuration also exposes block attention-residual organization. Do not substitute a plain residual-add implementation simply because tensor shapes happen to agree. Likewise, SiTU is not interchangeable with a default SwiGLU activation: the checkpoint-dependent activation and scaling must survive expert dispatch, quantization, fusion, and reduction.

Image or video processing adds a vision encoder and transport path before language inference. Its memory and CPU-transfer overhead must be budgeted separately from text tokens. A text-only benchmark does not certify multimodal throughput.

GLM 5.3: architecture

Data flow

Tokens → dense prefix → MLA latent cache + DSA index selection → routed/shared experts → repeat → output; optional MTP → target verification.

How the parts work together

The configuration describes MLA with a separate sparse-attention indexer. The model first constructs representations that make token-history storage cheaper than retaining a separate full key/value vector for every query head. The indexer then selects a limited subset of history for the more expensive attention operation. Compression of what is stored and sparsification of what is read are distinct optimizations.

A dense prefix is followed by routed MoE layers. Shared experts provide a common feed-forward contribution while selected routed experts specialize the token transformation. The router uses its own numerical precision and score function; expert quantization is not permission to quantize router decisions without validation.

The index-selection frequency exposes reuse across layers. Reusing index selections can avoid repeated work, but correctness depends on the implementation’s layer boundaries and index cache. It is not equivalent to asking every layer to select a fresh arbitrary top-k set.

The multi-token-prediction (MTP) extension can propose multiple steps for speculative serving. It does not convert the main model into a dense small model. Generation remains a target-model process with draft verification and cache bookkeeping.

GLM 5.3 Flash: architecture

Data flow

Vision/text → hybrid attention and MoE blocks with four residual streams → text head. KDA layers maintain recurrent state; sparse MLA layers read selected token history. MTP proposes tokens, and the serving engine must verify them with the target and commit the corresponding accepted state.

How the parts work together

Most text layers use KDA, while periodic NoPE sparse-MLA layers retrieve selected history. NoPE means that those attention projections do not use the ordinary rotary-position component; it does not mean that the whole model has no way to process sequence structure. The attention indexer includes pooled compression and a tail-selection mechanism.

Manifold-constrained hyper-connections maintain multiple residual streams and constrain how information mixes between them. The repeated Sinkhorn normalization configured for these connections is a specific model operation, not a generic replacement for the RMSNorm layer. Fusing residual communication must preserve that transformation.

The MoE has many more resident experts than each token activates. Its shared path, dense prefix and router remain part of the total compute and memory budget. A vision stack maps images and video frames into the text network’s representation; limiting image count is an admission-control decision as well as a preprocessing decision.

The native MTP layer is served through different APIs in the two engines. SGLang’s current recipe uses the EAGLE algorithm spelling for this native MTP path. That does not mean the model is using an unrelated external EAGLE checkpoint.

The architecture facts above are drawn from the publisher card and configuration; the workload consequences are analytical interpretation. glm-5.3-flash-CARD glm-5.3-flash-CFG

Memory and performance consequences

The publisher rounds the model to 320B total / 18B active. Pinned Hub metadata for both official precision variants reports 321,323,031,390 parameters; the catalog uses that checkpoint total for weight-only arithmetic. The publisher's active-parameter count has not been independently reconstructed. Packed NVFP4 arrays and their scale tensors cannot be counted as if every stored scalar were an original model parameter. glm-5.3-flash-META

The official FP8 index reports 328,326,771,576 serialized tensor bytes (328.33 decimal GB); BF16 reports 642,646,653,816 bytes (642.65 GB). Runtime memory also includes caches, recurrent state, temporary buffers and any loader repacking. glm-5.3-flash-INDEX glm-5.3-flash-BF16-INDEX

Budget recurrent KDA state and sparse token cache independently. SGLang’s cookbook explicitly warns that its default Mamba-to-full-memory ratio is generic. Too little state capacity caps running requests; too much starves token history. Derive a candidate split from real request lengths and boot-log pool sizes instead of blindly maximizing the ratio.

For a simple state-size illustration, 34 × 64 × 128 × 128 × 4 bytes is 142,606,336 bytes = 136 MiB per sequence for the FP32 state matrices alone, excluding convolution state, MTP state and implementation overhead. This is not the final CUDA allocation and cannot be divided by EP or DCP unless the source path shards that state accordingly.

The numeric examples are calculations from stated dimensions and assumptions, not measured allocations. Memory mathematics explains the formulas and their limits. glm-5.3-flash-CARD glm-5.3-flash-CFG HW

The NVFP4 group targets the routed-expert projection weights and activations in zero-based main layers 3–44, with group size 16. A second group targets MTP layer 45's routed experts using 8-bit floating-point weights in 128×128 blocks and dynamic 8-bit activations. KV and deployment contract

SGLang's CUDA recipe pairs Blackwell FP8 KV with TRT-LLM DSA, or BF16 KV with TileLang DSA. Change the dtype and both DSA backends together; the cookbook says CUDA TileLang DSA plus FP8 KV is not a valid pairing for this model. Verify the exact image because this is a documented path, not a local execution result. glm-5.3-flash-GR

Pin the model, tokenizer/processor, config and engine/container revisions together. Establish target-only quality before comparing quantized KV or speculation. A root BF16 dtype does not mean every stored tensor is BF16, and casting quantized weights does not recover the original reference. See the precision primer.

GLM 5.3 Flash: serving on 8×B300

Status: unbenchmarked local recommendations. The upstream recipes are evidence of documented support, not a benchmark of your node.

Engine and topology

Use one TP4 target-only process as a starting candidate, then compare a second independent TP4 replica against a TP8 process. SGLang’s Blackwell cookbook selects FlashInfer TRT-LLM MoE; vLLM provides an explicit TP4 FP8 recipe and an optional TP4-prefill plus TP4-decode layout.

First determine whether prefill interference warrants prefill/decode separation. The vLLM recipe requires matching KDA convolution-state layout, KV layout and speculative depth on both sides. A KV-only copy that omits recurrent state is not a correct migration. SGLang documents its PD route as a preview with dummy-weight mechanical checks only; it lacks real-weight load/accuracy qualification, and its current documented PD path does not start with speculative decoding. Keep speculation off and both roles at the same TP size for that separate probe.

The vLLM Flash recipe still contains historical integration/version guidance and differing FlashInfer minimums (0.6.17 in prerequisites versus 0.6.18 in troubleshooting). Resolve those requirements against the selected image; the recipe alone does not certify every release or nightly.

For structured responses, the current SGLang recipe resolves the reasoning parser to glm45 and the tool-call parser to glm47; vLLM's current recipe uses glm47 for both. Verify the returned fields on the pinned image.

Use natural MTP acceptance. Test the cookbook’s five-step, top-k-one configuration against target-only operation at high load. A speculative low-latency win can become a throughput loss when verification competes with a large batch.

Experiment sequence

Compare target-only operation (omit speculation flags) with 1/3/5 draft steps; TP4 versus TP8; independent replicas versus 4+4 disaggregation; the supported KV/backend pairs (FP8 + TRT-LLM DSA versus BF16 + TileLang DSA in SGLang CUDA); controlled KDA pool sizes. First capture actual GPU memory, compute capability, peer topology and software versions with python scripts/preflight.py. Then resolve immutable model metadata, inspect the rendered profile and run the target-only correctness suite. Profiles live in profiles.

Acceptance gates

A successful load is necessary but insufficient. Require valid streaming framing, finite outputs, correctly separated reasoning, valid tool calls where supported, repeatable quality tests, bounded memory at load, and correct cache/state behavior after cancellation. Only then compare latency and throughput.

For production, place one sharded model process group inside a pod that owns its whole GPU group. Do not make eight independent KServe replicas and expect them to form TP8. Start with colocated prefill and decode; adopt disaggregation only after it wins the workload comparison and state transfer is correct. KS KSLLM

Parameters are not magic constants

The profile’s context cap is an application policy. Tensor parallelism is a starting layout. Memory utilization reserves room for non-weight allocations; changing it can trade cache space against startup headroom. Batch-token and sequence caps trade prefill efficiency against memory and queueing. Speculative depth trades draft/verification cost against naturally accepted tokens. Each must be varied one at a time before interaction testing.

Deployment rendering boundary

Read architecture first. The renderer emits a custom-container InferenceService in Standard mode. It does not apply, install controllers, create PVCs, label nodes or download models. It is not a fabricated validated LLMInferenceService disaggregation deployment.

Provide a real digest, prepopulated read-only model PVC, measured CPU/host-memory requests and a node label actually present in the cluster. The default superstorm.ai/gpu-class=B300 is a label you must deliberately assign after inventory, not an automatic NVIDIA label. A single pod allocates the entire profile's GPU group on one node. Eight TP1 replicas require eight separate allocations/routing; this example keeps replicas at one.

The initial 8Gi shared-memory size and 30-minute startup allowance are editable safety candidates, not measured needs or a promise about cold-start time. Shared memory consumes the pod's host-memory budget. Startup/readiness health paths and graceful termination must be exercised against the actual image and KServe version. GPU topology and CPU locality require cluster scheduling policies beyond a label.

The renderer checks the SHA-256 digest suffix and basic image-reference structure but does not contact the registry to prove the image exists. It explicitly disables automatic service-account token mounting, a field supported by the KServe 0.21.0 CRD. It adds no credential mounts or external-service calls. Its local tests validate structure and guards, not admission against your installed CRDs. Before deploying, use kubectl apply --dry-run=server, inspect the rendered pod and confirm offline checkpoint/drafter availability, parser correctness, runtime cache paths and resource headroom. Require gateway authentication before external exposure.

profiles/README.md

Launch experiments, not performance promises

The profile index lists all 34 experiments.

Every JSON file is populated with a model, variant, engine, GPU topology, arguments, evidence and limitations. None was run on a B300 in this environment. candidate means an evidence-informed experiment; compatibility-probe means an additional unresolved loader or API gate; blocked cannot be executed by the launcher.

The launcher prints a command by default. Execution requires a local model directory containing config.json and a superstorm-revision.json provenance file whose immutable Hugging Face commit matches the profile's model_revision. Produce the metadata with scripts/fetch_metadata.py --ref <model_revision>, then separately obtain authorized weights for that revision. This repository does not download weights. An external drafter needs its own directory and matching draft_revision provenance. The launcher rejects snapshots marked INCOMPLETE.txt.

python scripts/launch.py --profile profiles/qwen3.8-27b.bf16.vllm.baseline.json
python scripts/launch.py --help

For an actual launch, add --execute --accept-unbenchmarked --model-dir /models/exact-revision. Probe profiles additionally need --allow-compatibility-probe. Any remote-code enablement needs --allow-reviewed-remote-code; audit the code at that revision first. Do not expose the service publicly without an authenticated gateway.

auto cache precision can resolve differently across exports. The Qwen 27B SGLang profiles explicitly choose BF16 KV as a local controlled comparison; the current cookbook pins FP8 E4M3 KV. These profiles do not reproduce its measurements. Record the vLLM effective dtype and change it deliberately for a matched comparison. Weight precision is independent of KV and recurrent-state precision. Effective engine help, loader logs and correctness tests remain authoritative; CLI flags were not exercised against installed engines here.

The Qwen Flash Next SGLang probe follows the exact NVIDIA TP1 recipe added in PR 41046, whose source marks the cell verified:false. Its 64K context cap, 32-request cap and 0.82 memory fraction are local unbenchmarked additions. The GLM 5.3 SGLang profile uses glm47 for tool calls and glm45 for reasoning, as required by its cookbook.

Do not run all profiles simultaneously. gpu_count is the GPU allocation for one instance, not a promise all requested models fit together. Independent one-GPU replicas need distinct GPU assignments and ports. Expert parallelism redistributes existing ranks: it is not another GPU-count multiplier.

Source recipes sometimes use more aggressive graph, symmetric-memory and pool settings. Those are intentionally not copied into every baseline. See the model's serving report and benchmark protocol.

reports/DECISIONS.md

Decision record

ADR 001: Separate model architecture from export producer

The same family can have native, NVIDIA, RedHat and Inferact artifacts with different quantization contracts. Keep each under the originating company and record producer-specific repository IDs. Rejected alternative: one flat “FP4 models” list that hides lineage and loader differences.

ADR 002: Use evidence stages instead of a binary supported flag

A model can be registered yet fail to import, load mixed scales, preserve state or parse tool calls. Record source evidence, compatibility probes, blocked paths and local benchmark status separately. Rejected alternative: a model-card widget means full production support.

ADR 003: Do not select eight-way tensor parallelism by habit

Large MoE targets and small dense targets stress different resources. Compare exact TP/DP/EP layouts and per-GPU replicas under the same node-wide workload. Rejected alternative: every model must use all eight GPUs in one tensor-parallel group.

ADR 004: Keep the control plane separate from the inference runtime

KServe/Kubernetes govern placement, health and rollout; vLLM/SGLang execute numerical inference. First validate a one-node target-only runtime, then add orchestration and only measured-benefit disaggregation. Rejected alternative: use a control-plane product as evidence of a faster kernel.

ADR 005: Metadata and image pins precede production

Resolve mutable model IDs and nightly tags to immutable identities, preserve raw metadata and compare outputs. Keep current source/release observations without claiming tested nightly binaries. Rejected alternative: a moving latest command is reproducible.

ADR 006: State what each parameter count includes

Keep publisher headlines, main-model counts, serialized auxiliary parameters and stored tensor bytes separate. GLM 5.3’s MTP tensors explain why its approximately 743B main model has a larger checkpoint count. DeepSeek’s competing recipe headlines still lack a reconciled exact census. Uniform byte estimates using rounded counts remain illustrations; runtime memory additionally depends on the loader, sharding, caches and workspaces.

These are engineering decisions derived from the framework comparison, source review and memory analysis. They are not empirical performance results.

Utilities and trust boundaries

All tools use the Python standard library. launch.py requires a separately installed engine only when execution is explicitly requested. No script installs dependencies or model weights automatically. Use Python 3.10 or newer; local tests were run on the version reported in VALIDATION.md.

Treat profile JSON and model code as trusted executable inputs: these tools do not sandbox arbitrary profiles or remote model implementations. CLI guardrails prevent common accidental actions, not malicious operator input. The launcher validates checkpoint identity and config metadata hash, not the weight shards. Obtain and independently verify all weights from the same immutable commit. A metadata-only directory cannot successfully serve until the matching authorized weights and any required processor/tokenizer files have been added.

Metadata retrieval intentionally excludes full tokenizer vocabularies, weight files and executable Python implementations. Optional missing files are recorded. API auth uses HF_TOKEN from the environment and strips it across cross-host redirects. The benchmark uses BENCH_API_KEY, rejects credential-bearing URLs and never follows redirects. Neither tool prints tokens or dumps the environment. The metadata downloader is covered by offline mocks; the source HTTP retrievals recorded by this audit are separate from an end-to-end integration test of this downloader against the Hub.

The streaming probe implements the usual one-JSON-object-per-SSE-data-line interface exposed by these chat endpoints and accepts one completion per request (n=1). General multi-line SSE event assembly is outside its scope. It is a closed-loop integration probe, not an open-loop saturation benchmark or exact per-token profiler. Requests may generate server-side costs; the tool only sends the explicit JSONL workload, after validating the workload and opening a new output file. An interrupted process can leave an incomplete output file. Returned tools/code are not executed. --timeout bounds socket operations and is checked between bounded line reads; it is not a strict wall-clock cancellation guarantee.

The launcher rejects synthetic acceptance in both environment settings and speculative configuration. Profile topology/context fields must match their engine arguments. validate_repo.py also checks model/catalog and profile/catalog equality, immutable revision consistency, duplicate identities, uncatalogued model/profile records and strict JSON syntax. These checks do not certify model weights, engine behavior or publisher claims.
