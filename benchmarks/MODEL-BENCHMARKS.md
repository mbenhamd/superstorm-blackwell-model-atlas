# Choose benchmarks for the model and the decision

**All runs on this page are proposed. No model-quality or GPU result has been measured in this atlas.** Use the [engine experiment roadmap](../reports/EXPERIMENTS.md) to choose the system change and this page to choose the evidence that would justify it. The family validation pages below define the exact model/export prerequisites.

## Instructions that needed more detail

| Gap in the earlier plans | Required instruction | Why it changes the decision |
| --- | --- | --- |
| Lists of precision, context and parallelism settings without a specific quality test | Select a task, scorer and reference before each sweep | Faster generation can conceal lost instruction following, retrieval or tool correctness. |
| One generic quality threshold | Predeclare thresholds by critical task, language, modality and context bucket | A mean score can conceal a regression in the workload that matters. |
| A benchmark name without its evaluation contract | Pin dataset, split, selected item IDs, scorer, prompt construction, reasoning budget and output extraction | Two runs bearing the same benchmark name can measure different tasks. |
| Several profile differences attributed to one feature | Compare a matched control or label the result as a complete-configuration comparison | KV dtype, EP, autotuning, cache allocation and speculation can change together. |
| Successful HTTP/SSE completion treated as a useful answer | Track protocol completion, task success and latency compliance separately | A length-limited or filtered completion can pass transport checks and still fail the task. |
| Throughput evidence without saved answers | Use an answer-retaining evaluator and link request IDs to scores | The included probe does not preserve answer text or tool arguments for later scoring. |
| Benchmark scores used to choose a serving engine directly | Measure quality first, then service performance for the qualified configuration | Publisher scores do not measure the local engine, export, hardware or load. |

These are methodological corrections and proposed engineering choices. They do not assert that an unexecuted configuration works.

## A small benchmark menu with a purpose

Choose the relevant rows, plus held-out examples from the actual application. Do not run every public suite merely to produce a large table. Here, “held out” means withheld from local tuning; it does **not** establish that the examples were absent from model training.

| --- | --- | --- |

Benchmark sources above define their tasks and evaluators. Their selection for this atlas is a proposed use, not evidence that they already provide a working adapter for every listed model. Check the pinned harness's endpoint, template and reasoning/tool handling before interpreting a score. If an adapter is missing, record the block and the required adapter validation; do not substitute an unlabelled prompt format.

## Design one comparison before scaling it

1. **State the decision.** Example: decide whether one exact Qwen 27B NVFP4 export preserves the declared coding and image quality requirements while increasing node capacity. First compare it with the qualified BF16 reference under matched serving settings. A separate topology experiment can then spend the freed memory. Do not attribute both changes to weight precision.
2. **Freeze the evaluation contract.** Record benchmark version, dataset revision/split, selected item IDs/hash, scorer commit, metric definition, prompt adapter, answer extractor, few-shot examples, system prompt and model-specific chat template. Record image processor and tool schemas where applicable. Keep reference answers out of generation inputs. Use a development set to choose settings and a held-out set for the final decision. Keep the final set out of local quantization calibration, prompt/backend/precision selection and tuning. If an export does not disclose its calibration data, record that overlap is unknown; identify public-set training contamination uncertainty separately.
3. **Define budgets and failure policy.** Pin all effective sampling settings, including temperature/top-p and any top-k/min-p/penalties or generation-config defaults, plus attempts, reasoning effort, output cap, stop strings, timeouts, retries and agent/tool budgets. Same effort labels across models need not mean equal computation. Compare both a declared budget policy and observed useful-answer quality, generated tokens and wall time. Keep reasoning and final-answer latency separate where the endpoint exposes them. Retain observed reasoning/final/total token counts when available; do not infer hidden counts from a single combined usage field.
4. **Check context before each request.** Serialized text, tool schema, retained history and image tokens plus reserved generation must fit both model and launch limits. Record the actual token counts and truncation policy. A context-limit rejection is a recorded infeasible point, not permission to silently shorten a benchmark or discard it.
5. **Run paired quality and service campaigns.** Use the same item IDs and frozen payloads for within-model A/B tests. Establish low-load quality, then score a preselected subset under realistic load, cache hits/eviction and cancellations. Replay cancelled sessions from the prescribed conversation state and score subsequent responses. Use enough independent repeats for the chosen uncertainty analysis; a screening subset is not a full benchmark score.
6. **Explain acceptance.** Predeclare absolute task requirements and allowed degradation per critical stratum. For quality differences, estimate paired uncertainty at the independent item/session level, retaining correlations between multiple turns or attempts. A failed significance test is not evidence of equivalence. For a higher-is-better score, one proposed rule is Δ = candidate − reference: require the chosen lower confidence bound to be at least −allowed regression, and require the absolute task threshold to pass under its predeclared uncertainty rule. A confidence interval crossing the allowed regression boundary is inconclusive; one wholly below it fails the regression requirement. Reverse the direction for lower-is-better metrics. Freeze tuning budget and candidate count to limit selection bias; confirm the selected candidate on held-out work.

For within-model engine comparisons, require the same effective tokenization and template where supported. If endpoint serialization differs, investigate and either correct it or report a complete-serving-stack comparison. For **cross-model** comparisons, use identical task content and scorer with each model's valid template/tokenizer. Report their actual token counts; equal token counts across different tokenizers are not necessarily equal work. Rank useful task completion per elapsed time and resource budget, with the quality/latency constraints stated. Keep pure token-throughput charts within an explicitly comparable tokenization scope.

## Separate completion, correctness and goodput

| Outcome | Required evidence | Interpretation |
| --- | --- | --- |
| Protocol completed | Valid response framing and recognized finish reason | The request reached a protocol endpoint, not necessarily a useful answer. |
| Task succeeded | Saved response plus a fixed scorer, tests or reviewed rubric | The answer met the task's definition; valid tool JSON alone is insufficient. |
| Latency objective met | Request timing with the declared start/end and budget | A fast refusal or truncated answer can satisfy timing while failing the task. |
| Quality-adjusted request goodput | Join all three outcomes for the **same request ID**; count qualifying requests over full measurement wall time | Unscored responses do not qualify. Report offered, completed, scored, failed, filtered, truncated and retried counts. |
| Latency-SLO goodput for a quality-qualified configuration | A separate quality campaign passes; the load run measures successful requests within latency budgets | This does not show that every timed answer was correct. Do not multiply throughput by an unrelated average benchmark score and call it measured quality-adjusted goodput. |

For multi-turn tools or agents, score the complete task/episode. Count unique successful episodes and include every model call, tool step and retry in elapsed time and resource accounting. Request throughput is a separate diagnostic; it is not completed-task throughput.

The local [streaming probe](run_streaming.py) accepts `length` and `content_filter` as recognized protocol endings. Its `ok` and `successful_requests_per_second` are transport-level observations. It does not save answer text, reasoning or assembled tool calls; it cannot provide a quality artifact or score outputs after the run. It sends a fixed JSONL list and does not execute tool results or run an agent loop. Add an external answer-retaining evaluator for quality, and an open-loop client for controlled arrival-rate experiments. No such evaluator or adapter is implemented by this documentation update.

A `length` finish is a censored generation; report it even if a task scorer accepts the partial answer. Keep task success and truncation as separate fields and predeclare whether truncation disqualifies service acceptance. A refusal/filter response needs the task's policy-aware label. Retries consume time, tokens and requests: report first-attempt and retry-assisted success separately. Count resource consumption from failed attempts as well.

## Minimum artifacts and decisions

Extend each [experiment record](experiment.template.json) with a quality suite manifest. For multiple suites, keep one manifest per suite and reference them through `quality_evaluation.additional_suite_manifests`. Each manifest must bind the selected items, payloads, raw answers and scores using stable item/request/attempt IDs. Preserve model and engine identities, effective settings, usage, finish reasons, timing, tool traces where applicable, and scorer errors. The template is manual: repository validation checks JSON syntax, not whether these fields are complete or scientifically sound.

When using a model judge, pin its identity, prompt, rubric and parsing, and audit a sample with human labels. Report disagreement and judge failures. Prefer executable tests or deterministic checks when they represent the task. Neither a judge score nor a benchmark aggregate proves that arbitrary application answers are factual.

Publish a decision table for each family: exact baseline/candidate, relevant task scores and paired uncertainty, failure/truncation counts, observed reasoning/output budget, whole-node goodput definition, tail latency, peak memory, and **promote / reject / inconclusive / blocked** with a reason. Start with a small fixed qualification campaign, expand only passing candidates, and retain the baseline for rollback. The next operator work is to select the application workload, thresholds, pinned evaluator/adapters and actual B300 environment; those inputs cannot be inferred from publisher cards.
