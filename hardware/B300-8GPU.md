# Hardware target: eight B300 GPUs per node

## Verified hardware facts versus supplied inventory

NVIDIA’s specifications, rechecked **October 16, 2026 UTC**, list a DGX B300 with eight B300 GPUs, 288 GB per GPU and approximately 2.3 TB aggregate GPU memory. Its CUDA GPU table identifies B300 as compute capability **10.3**. Those are architectural references; the supplied **B300 SXM6-AC** label does not identify a complete DGX-equivalent bill of materials. CPU, RAM, NVMe, NICs, firmware, power and cooling remain OEM-specific until inventoried. [HW](https://docs.nvidia.com/dgx/dgxb300-user-guide/introduction-to-dgxb300.html) [CC](https://developer.nvidia.com/cuda/gpus)

Eight times 288 is 2,304 advertised GB. If those units are interpreted as decimal bytes, that is approximately 2,145.77 GiB. Treat this as a unit-conversion illustration, not a prediction of `nvidia-smi` output: query the memory actually exposed by the driver and allocator. Neither advertised total nor driver-visible total is all available for weights.

## Preflight before tuning

Collect a read-only inventory on the actual inference host: the eight intended devices, driver-visible memory, compute capability, driver/CUDA versions, peer-access topology and process ownership. Record CPU architecture so x86_64 B300 and Grace-based GB300 software images are not confused. Power limits, GPU partitioning, CPU/NUMA placement, NIC affinity and cooling conditions belong in the hardware description because they can change the meaning of a performance comparison.

Do not treat a workstation RTX Blackwell measurement as an HGX B300 measurement. SM12x devices, B300 SM10.3, and B200 SM10.0 have different kernel and topology requirements. Likewise, GB300’s host and memory architecture is not an automatic match for an x86 SXM node. [CC](https://developer.nvidia.com/cuda/gpus) [qwen3.8-27b-GR](https://docs.sglang.io/cookbook/autoregressive/Qwen/Qwen3.8-27B) [deepseek-v4-flash-0731-VR](https://recipes.vllm.ai/deepseek-ai/DeepSeek-V4-Flash?features=tool_calling,reasoning&hardware=b300)

CUDA 13.0's compiler explicitly supports `sm_103`, `sm_103a` and `sm_103f`. This supports a CUDA 13-era **native compilation target** claim; it does not show that an arbitrary engine image contains the required attention, MoE, quantization or recurrent-state kernels. Compatible generic cubins/PTX can also run under NVIDIA's compatibility rules, while architecture-specific `a` targets have narrower compatibility. Record the actual image digest, CUDA runtime/compiler, driver, PyTorch and kernel-library versions, compiled targets and selected backend. A successful import is not evidence of the intended GPU kernel executing. [RR-HK-CUDA13-NVCC](https://docs.nvidia.com/cuda/archive/13.0.0/cuda-compiler-driver-nvcc/index.html) [RR-HK-BLACKWELL-COMPAT](https://docs.nvidia.com/cuda/blackwell-compatibility-guide/index.html)

## Capacity plan

Use this budget for each GPU:

```text
target weights, scales and resident repacked copies
+ draft/MTP weights actually loaded
+ persistent attention KV, sparse-index and compression caches
+ recurrent/conv state, prefix snapshots and speculative rollback slots
+ temporary prefill/decode/verification activations
+ graph captures, kernel/library workspaces and allocator overhead
+ communication and expert-routing buffers
+ explicit safety headroom
<= memory exposed to the process
```

Shard each term only across the process group that actually shards it. TP can shard heads or linears; EP distributes experts; DP may replicate attention; DCP partitions decode context. None is a universal divisor for the entire memory budget. [kimi-k3-GR](https://docs.sglang.io/cookbook/autoregressive/Moonshotai/Kimi-K3) [glm-5.3-flash-GR](https://docs.sglang.io/cookbook/autoregressive/GLM/GLM-5.3-Flash) [qwen3.8-27b-GR](https://docs.sglang.io/cookbook/autoregressive/Qwen/Qwen3.8-27B)

On the advertised 288 GB basis, fractions `0.88`, `0.90` and `0.92` leave arithmetic complements of **34.56**, **28.80** and **23.04 GB per GPU**. These are accounting illustrations, not guaranteed free-memory reserves. vLLM's executor fraction and SGLang's static-memory fraction have different implementations; use the [engine-specific accounting](../reports/memory-math.md#executor-fractions-are-not-reserved-memory) and observed per-rank peaks. A low fraction can leave insufficient cache after loading large weights, while a high fraction can leave insufficient space for runtime peaks.

## Recommended first node layouts

| Workload family | First comparison | Why this is a candidate, not a universal best |
| --- | --- | --- |
| Kimi K3 | One 8-GPU target | Weight footprint rules out casual per-GPU replication |
| GLM 5.3 BF16 | TP8 capacity/loader probe | About 1.507 TB serialized tensors cannot fit into four advertised 288 GB GPUs; TP8 has room for a capacity experiment, not an established serving result |
| GLM 5.3 FP8 | TP8 | Conservative capacity and supported sharding baseline |
| GLM 5.3 NVFP4 | TP4 versus TP8 | May permit two replicas while retaining useful cache |
| GLM Flash | Two independent TP4 groups versus TP8 | Tests node goodput against per-request cooperation |
| DeepSeek 0731 | vLLM TP1/DP4 with EP, plus documented SGLang TP4; then eight-GPU experiments | Distinguishes published four-GPU configurations from local scaling hypotheses |
| Qwen 27B / Gemma 31B | TP1 replicas versus TP2/4 | Small enough to evaluate communication-free replicas |
| Qwen Flash Next | NVIDIA/vLLM TP8 baseline; documented SGLang TP1 candidate; TP4 capacity probe | The SGLang B300 recipe is unverified; n-gram and auxiliary precision affect capacity |
| Mistral Medium | Publisher TP8 baseline, then TP2/4 comparisons; TP1 capacity probe | Dense compute and full-history KV change the trade-off |

These combine publisher configurations and local experiments, as labeled; none is a measured B300 performance ranking here. The GLM 5.3 full checkpoint includes about 9.95B MTP parameters beyond its approximately 743.38B main model. Budget the modules actually loaded by the chosen target-only or speculative path. See [comparison](../reports/comparison.md) and [memory accounting](../reports/memory-math.md) for exact artifacts and evidence.

Two TP4 replicas occupy all eight GPUs and duplicate the weights and caches. They can improve request concurrency only if each independently fits and the workload benefits. One TP8 replica also occupies all eight GPUs, so an overlapping TP8 replacement or separate TP8 prefill/decode pair requires another eight GPUs. On this one-node budget, plan an interruption for a TP8 replacement, or first qualify a smaller replica topology and its temporary capacity loss. [KServe capacity and rollout](../frameworks/kserve/ARCHITECTURE.md#design-within-the-eight-gpu-budget)

## Blackwell-specific optimization order

### B300 attention is not a B200 or RTX measurement

NVIDIA identifies B200/GB200 as compute capability 10.0, B300/GB300 as 10.3, and RTX 5090/RTX PRO 6000 Blackwell as 12.0. The Blackwell tuning guide also documents different shared-memory limits for 10.0 and 12.0. A common marketing generation or NVFP4 capability does not make their attention kernels interchangeable. [ATTR-HW-CC](https://developer.nvidia.com/cuda/gpus), [ATTR-HW-TUNING](https://docs.nvidia.com/cuda/blackwell-tuning-guide/index.html).

The FA4 paper reports exponential throughput of **32 operations/clock/SM on B300/GB300**, compared with **16 on B200/GB200**. Its B200 softmax bottleneck and headline BF16 results therefore need a B300-specific interpretation. In the inspected upstream FA4 source, SM103 detection disables exponential emulation by default; the detailed [FA4 explanation](../reports/attention-and-fa4.md) records that source revision and distinguishes hardware capability, library code and actual engine integration. These are reasons to inspect the selected kernel, not a measured B300 speedup. [FA4 paper v1, §2.2](https://arxiv.org/html/2603.05451v1).

First establish an image that loads the correct artifact with finite, coherent outputs. Next verify kernel selection and mixed-format behavior. Only then compare FP8 versus NVFP4, attention backends, CUDA graph modes, batch caps, cache precision and speculative decoding. A newer kernel that is incompatible with block scales, SiTU or state replay can return incorrect results without an obvious crash. The Kimi fixes provide a concrete example. [KIMIPR](https://github.com/sgl-project/sglang/pull/35077) [KIMIVPR](https://github.com/vllm-project/vllm/pull/52406) [GQUANT](https://github.com/sgl-project/sglang/blob/877be2974aa151a984e52822c028276c2b1e9303/python/sglang/srt/layers/quantization/modelopt_quant.py)

Inspect whether time is spent in expert GEMMs, attention, routing, all-to-all, reductions, host scheduling, tokenization or memory movement. Changing a precision format cannot remove an unrelated queueing or network bottleneck. For low-concurrency dense models, launch and synchronization overhead can dominate; at longer contexts, cache bandwidth can dominate. This is a workload hypothesis to test with traces.

## CPU, storage, network and power

Use local immutable checkpoint staging where operationally possible. Cold starts include downloading, deserialization, repacking, compilation and graph capture; do not report them as steady-state decoding. Mistral’s two weight layouts must not both be staged by accident. K3 can require terabyte-scale storage and loading headroom. [mistral-medium-3.5-TREE](https://huggingface.co/mistralai/Mistral-Medium-3.5-128B/tree/main) [kimi-k3-NV](https://huggingface.co/nvidia/Kimi-K3-NVFP4)

For multi-node or prefill/decode transfer, inventory NIC-to-GPU affinity, link type, effective bandwidth, congestion and routing. NVLink within a node is not evidence of equivalent bandwidth between nodes. A separated prefill/decode layout should transfer every required token and recurrent-state component with compatible layouts. [glm-5.3-flash-VR](https://recipes.vllm.ai/zai-org/GLM-5.3-Flash) [KSMULTI](https://kserve.github.io/website/docs/model-serving/generative-inference/multi-node) [KSLLM](https://kserve.github.io/website/docs/model-serving/generative-inference/llmisvc/llmisvc-overview)

Do not use NVIDIA’s DGX system power specification as the measured power of this OEM node. Record wall power or a documented telemetry scope during the experiment. Performance per watt and cost per million successful tokens are derived metrics that need actual energy and pricing inputs; this atlas invents neither.
