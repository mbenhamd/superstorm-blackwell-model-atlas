# Hardware target: eight B300 GPUs per node

## Verified hardware facts versus supplied inventory

NVIDIA documents a DGX B300 with eight B300 GPUs, 288 GB per GPU and approximately 2.3 TB aggregate GPU memory. Its CUDA GPU table identifies B300 as compute capability 10.3. Those are useful architectural references, but your supplied **SXM6-AC** label does not identify a complete DGX-equivalent bill of materials. CPU, RAM, NVMe, NICs, firmware, power and cooling remain OEM-specific until inventoried. [HW](https://docs.nvidia.com/dgx/dgxb300-user-guide/introduction-to-dgxb300.html) [CC](https://developer.nvidia.com/cuda/gpus)

Eight times 288 is 2,304 advertised GB. If those units are interpreted as decimal bytes, that is approximately 2,145.77 GiB. Treat this as a unit-conversion illustration, not a prediction of `nvidia-smi` output: query the memory actually exposed by the driver and allocator. Neither advertised total nor driver-visible total is all available for weights.

## Preflight before tuning

Run `python scripts/preflight.py --output preflight.json` on the actual inference host. It runs read-only version and topology queries; it does not set GPU clocks, power limits, MIG mode, network devices or kernel parameters. Confirm eight intended devices, compute capability, driver/CUDA compatibility, peer-access topology and process exclusivity. Record CPU architecture so x86_64 B300 and Grace-based GB300 software images are not confused.

Do not treat a workstation RTX Blackwell measurement as an HGX B300 measurement. SM12x devices, B300 SM10.3, and B200 SM10.0 have different kernel and topology requirements. Likewise, GB300’s host and memory architecture is not an automatic match for an x86 SXM node. [CC](https://developer.nvidia.com/cuda/gpus) [qwen3.8-27b-GR](https://docs.sglang.io/cookbook/autoregressive/Qwen/Qwen3.8-27B) [deepseek-v4-flash-0731-VR](https://recipes.vllm.ai/deepseek-ai/DeepSeek-V4-Flash?features=tool_calling,reasoning&hardware=b300)

## Capacity plan

Use this budget for each GPU:

```text
weights and repacked weights
+ persistent attention/index caches
+ recurrent-state pools and snapshots
+ temporary prefill/decode activations
+ communication and graph buffers
+ explicit safety headroom
<= memory exposed to the process
```

Shard each term only across the process group that actually shards it. TP can shard heads or linears; EP distributes experts; DP may replicate attention; DCP partitions decode context. None is a universal divisor for the entire memory budget. [kimi-k3-GR](https://docs.sglang.io/cookbook/autoregressive/Moonshotai/Kimi-K3) [glm-5.3-flash-GR](https://docs.sglang.io/cookbook/autoregressive/GLM/GLM-5.3-Flash) [qwen3.8-27b-GR](https://docs.sglang.io/cookbook/autoregressive/Qwen/Qwen3.8-27B)

## Blackwell-specific optimization order

First establish an image that loads the correct artifact with finite, coherent outputs. Next verify kernel selection and mixed-format behavior. Only then compare FP8 versus NVFP4, attention backends, CUDA graph modes, batch caps, cache precision and speculative decoding. A newer kernel that is incompatible with block scales, SiTU or state replay can return incorrect results without an obvious crash. The Kimi fixes provide a concrete example. [KIMIPR](https://github.com/sgl-project/sglang/pull/35077) [KIMIVPR](https://github.com/vllm-project/vllm/pull/52406) [GQUANT](https://github.com/sgl-project/sglang/blob/877be2974aa151a984e52822c028276c2b1e9303/python/sglang/srt/layers/quantization/modelopt_quant.py)

Inspect whether time is spent in expert GEMMs, attention, routing, all-to-all, reductions, host scheduling, tokenization or memory movement. Changing a precision format cannot remove an unrelated queueing or network bottleneck. For low-concurrency dense models, launch and synchronization overhead can dominate; at longer contexts, cache bandwidth can dominate. This is a workload hypothesis to test with traces.

## CPU, storage, network and power

Use local immutable checkpoint staging where operationally possible. Cold starts include downloading, deserialization, repacking, compilation and graph capture; do not report them as steady-state decoding. Mistral’s two weight layouts must not both be staged by accident. K3 can require terabyte-scale storage and loading headroom. [mistral-medium-3.5-TREE](https://huggingface.co/mistralai/Mistral-Medium-3.5-128B/tree/main) [kimi-k3-NV](https://huggingface.co/nvidia/Kimi-K3-NVFP4)

For multi-node or prefill/decode transfer, inventory NIC-to-GPU affinity, link type, effective bandwidth, congestion and routing. NVLink within a node is not evidence of equivalent bandwidth between nodes. A separated prefill/decode layout should transfer every required token and recurrent-state component with compatible layouts. [glm-5.3-flash-VR](https://recipes.vllm.ai/zai-org/GLM-5.3-Flash) [KSMULTI](https://kserve.github.io/website/docs/model-serving/generative-inference/multi-node) [KSLLM](https://kserve.github.io/website/docs/model-serving/generative-inference/llmisvc/llmisvc-overview)

Do not use NVIDIA’s DGX system power specification as the measured power of this OEM node. Record wall power or a documented telemetry scope during the experiment. Performance per watt and cost per million successful tokens are derived metrics that need actual energy and pricing inputs; this atlas invents neither.
