## Decision and applicability

**Proposed experiments; no GPU results.** The question is which exact export and serving configuration gives useful capacity for a hybrid dense, multimodal service while preserving its quality. This model's 48 recurrent-attention layers and 16 full-attention layers make state handling a separate qualification from ordinary KV-cache reuse. The current cards/configs of all three artifacts matched their atlas pins when retrieved again on 2026-10-15 UTC. [qwen3.8-27b-CFG](https://huggingface.co/Qwen/Qwen3.8-27B/raw/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0/config.json), [precision and provenance](precision.md).

Start with the [vLLM BF16 TP1 profile](../../../profiles/qwen3.8-27b.bf16.vllm.baseline.json) and [SGLang BF16 TP1 profile](../../../profiles/qwen3.8-27b.bf16.sglang.baseline.json). Qualify each pinned build before comparing engines. Resolve vLLM's `auto` KV dtype and match it to the other arm; the supplied SGLang profiles use BF16 KV, while upstream examples use FP8 KV. Weight format, KV dtype and recurrent-state dtype are three distinct controls. The NVIDIA export has mixed NVFP4/FP8 modules and an unresolved exporter-version discrepancy; neither a generic NVFP4 label nor an Inferact recipe qualifies these exact files. [qwen3.8-27b-NV-CFG](https://huggingface.co/nvidia/Qwen3.8-27B-NVFP4/raw/482ca0f3832238542f8f5295dde86b5f22711d80/config.json), [serving](serving.md).

The profiles cap context at 32,768 and active requests at 32. Begin with serialized inputs near 4K and 16K and output budgets of 128/1,024; include all template, reasoning-history and visual tokens in the length check. A 32K input plus output does not fit this cap. Longer input buckets and 128 active requests need separately qualified capacity settings. Native 262,144-token capacity and the publisher's 1M extension are subsequent experiments, with explicit positional overrides, memory and accuracy gates. Parser-free baseline profiles also need a pinned, qualified tool/reasoning configuration before they can evaluate those API features. [qwen3.8-27b-CARD](https://huggingface.co/Qwen/Qwen3.8-27B/raw/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0/README.md).

## Architecture and export experiments

| ID / hypothesis | Controlled experiment | Evidence and decision |
| --- | --- | --- |
| Q27-01 — Lower weight precision helps at a useful batch size. | Within each qualified engine, compare pinned BF16, official block FP8 and NVIDIA mixed NVFP4 at TP1, first concurrency 1 and 8, then 32 if feasible. Keep effective KV/state precision, payloads and cache state fixed. Inspect exclusions and selected kernels at load. | Save module/backend diagnostics, load/steady-state/peak memory, quality deltas and latency/goodput by workload. An unexpected fallback or quality failure disqualifies that arm. Distinguish reduced resident weights from increased cache reservation; a smaller file is not a measured speedup. |
| Q27-02 — Prefix reuse preserves both recurrent and full-attention state. | Replay identical histories cold, warm and after eviction; add divergent suffixes around the build's cache/chunk boundaries. Interleave unrelated sessions, cancel during prefill and decode, then repeat. Sweep sequence length at fixed active count, then active count at fixed length; vary the supported state/KV pool split only after measuring demand. | Record recurrent/convolution state slots, snapshots, KV occupancy, evictions, prefill reuse and allocation failures. Score planted answers against fresh-session controls. Stale cross-session content, lost suffixes or unrecovered pool allocation reject the candidate. Speed gains without correct state restoration do not pass. |
| Q27-03 — Thinking controls improve complete task outcomes. | Freeze thinking mode, all sampling fields, reasoning effort and `preserve_thinking` for each engine/export A/B. Separately compare supported effort levels or preservation policies on the same multi-turn tasks, recording the resulting serialized histories. | Report final-answer quality, first-answer latency, reasoning/final tokens, task completion time and retries. A preservation change changes the input and belongs to a separate service-policy comparison. Faster first reasoning output alone does not select a winner. |
| Q27-04 — Multimodal processing remains correct after export changes. | Use the same image bytes, ordering, crop/resize policy and processor revision across exports. Add bounded videos only after the exact endpoint qualifies; freeze decoded frame identities, timestamps and sampling policy. Vary resolution or frame count in separate runs. | Save visual-token counts, preprocessing/encoder time where exposed, TTFT, peak memory and image/video quality. Repeat text-identical requests with different images to detect cache-key mistakes. Frame-sequence input and a native video endpoint are different measurements; unsupported video is an applicability block. |
| Q27-05 — MTP repays draft, verification and rollback costs. | After Q27-01/02, compare the [SGLang target-only NVFP4 profile](../../../profiles/qwen3.8-27b.nvfp4.sglang.baseline.json) with its [MTP candidate](../../../profiles/qwen3.8-27b.nvfp4.sglang.mtp.json) in the same build. Verify that the exact checkpoint's MTP tensors load. Start with the documented settings, then change only supported depth settings. Repeat at low load and near saturation. | Retain natural accepted-length distributions with their denominator, draft/verification time, memory, rejection/rollback failures and quality. Include long coding, short chat and image-conditioned generation because acceptance can differ. Reject synthetic acceptance. MTP surviving a short chat does not establish hybrid-state correctness. |
| Q27-06 — Replication outperforms sharding for the intended traffic. | For the best qualified export compare eight TP1 replicas, four TP2 groups and two TP4 groups, using all eight GPUs and the same offered arrival trace. Count router/CPU resources and preserve session/cache-routing policy. Fix total-node admission/concurrency and log per-group batching/scheduler limits before separate capacity tuning. | Compare whole-node goodput, per-request tails, memory headroom and recovery after cancelling a busy request. Changed admission or batching policies require a complete-configuration comparison. Keep a separate single-group latency result; it cannot select node capacity. Dense MLPs provide no expert-parallel experiment. |

The thinking/image/video interfaces and MTP recipes are publisher/engine documentation; the experiment designs and selection criteria above are local proposals. A supported payload format does not establish benchmark validity or quality. [qwen3.8-27b-CARD](https://huggingface.co/Qwen/Qwen3.8-27B/raw/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0/README.md), [qwen3.8-27b-GR](https://docs.sglang.io/cookbook/autoregressive/Qwen/Qwen3.8-27B).

## Quality tasks chosen for this model

Use the same frozen examples across BF16/FP8/NVFP4 and engine arms. A small preregistered subset can screen failures; promotion requires the declared full evaluation or an explicitly bounded application claim. Keep tuning examples separate from the final quality set. Publisher scores motivate coverage; they supply neither the expected local score nor a production threshold.

| Task and primary source | Why it belongs here / controls and outputs |
| --- | --- |
| [IFBench](https://github.com/allenai/IFBench) — MBENCH-IFBENCH | Verifiable constraints exercise instruction following across quantization and thinking changes. Pin test data/verifiers and report prompt-level strict/loose results with failure categories. Score the final answer after the validated parser. The maintainer's temperature-zero evaluation is a distinct policy from Qwen's recommended sampled serving settings; label both if used. |
| [LiveCodeBench](https://github.com/LiveCodeBench/LiveCodeBench) — MBENCH-LCB | Executable code-generation tasks are useful for long decode and MTP acceptance. Freeze `release_v6` or an explicitly chosen newer date window, data revision, sample count, prompt adapter and evaluator limits; report pass@1 and truncations. `release_latest` is unsuitable for repeated A/B runs. A local score does not reproduce the card's v6 score without matching its harness. |
| [RULER v1](https://github.com/NVIDIA/RULER/tree/rulerv1-ns) — MBENCH-RULER-V1 | Retrieval, tracing and aggregation at increasing lengths can reveal state/precision regressions that a single needle misses. Freeze the RULER and linked NeMo-Skills commits, tokenizer, generated examples and task mix. Report task-by-length scores and failures. Modified cache-boundary cases are labelled local regressions, outside the standard aggregate. |
| [MMMU-Pro](https://github.com/MMMU-Benchmark/MMMU/tree/main/mmmu-pro) — MBENCH-MMMUPRO | Image-dependent reasoning checks the complete multimodal path. Choose `standard(10 options)` or `vision` and report them separately; pin prompt mode and preserve each image-placeholder mapping. Record per-subject accuracy and image tokens. A text-only score cannot qualify a mixed export for images. |
| [BFCL](https://github.com/ShishirPatil/gorilla/tree/main/berkeley-function-call-leaderboard) — MBENCH-BFCL | After parser qualification, use declared offline function-selection/argument and multi-turn categories. Report semantic call correctness separately from JSON validity. Pin the handler and tool environment; a category subset is not the overall leaderboard score. |
| Held-out application images and videos | Add document questions and temporal-order/counting questions with known answers and a written rubric. Include changed-image and reordered-frame controls. Report video completion and answer accuracy separately from single-image results; an image benchmark does not establish temporal understanding. |

## Run record and promotion

Use the [shared model benchmark guide](../../../benchmarks/MODEL-BENCHMARKS.md), [protocol](../../../benchmarks/PROTOCOL.md) and a filled [experiment manifest](../../../benchmarks/experiment.template.json). Predeclare quality floors and permitted regressions per relevant task, latency/error budgets, useful goodput improvement, memory reserve and uncertainty method. Unknown thresholds block promotion. Randomize A/B order, repeat independently, retain failed requests and report uncertainty on paired quality and service differences. If the improvement interval crosses the declared useful threshold, the decision is inconclusive.

Deliver raw outputs/scores, request records, effective dtype/kernel/state-pool logs, processor/template hashes, startup and cancellation evidence, plus a decision for each workload and mode. The [result schema](../../../benchmarks/result.schema.json) describes the HTTP/SSE probe only; it does not score code, tools, images, videos or quality, and does not turn SSE chunks into exact token timings. Empty results mean not measured.
