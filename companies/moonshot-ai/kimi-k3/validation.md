## What needs a decision

Determine whether each exact export and serving configuration preserves useful coding, tool and image quality while meeting the application's latency and capacity requirements on the same eight GPUs. The earlier instruction to sweep context and draft length did not identify a scorer, a matched target-only control, or which memory pool could cause a failure. The stages below make those distinctions observable. Use the [shared benchmark selection guide](../../../benchmarks/MODEL-BENCHMARKS.md), [protocol](../../../benchmarks/PROTOCOL.md) and [experiment record](../../../benchmarks/experiment.template.json) for dataset pins, paired uncertainty, request IDs and predeclared thresholds.

## Choose scored workloads for Kimi

Freeze item IDs, evaluator and adapter commits, sampling, reasoning effort, output extraction and generation limits before comparing engines or exports. Keep raw complete messages, including reasoning and tool fields, for the next turn. Kimi always reasons; its card requires preserved assistant history and offers `low`, `high` and `max` effort. A harness that drops `reasoning_content` is an adapter failure. [kimi-k3-CARD](https://huggingface.co/moonshotai/Kimi-K3/blob/f831ab66814297da540d832a5235f8e904f29d06/README.md).

| Suite / proposed use | Why it is useful here | Scoring and controls |
| --- | --- | --- |
| Frozen LiveCodeBench code-generation release and date range | Executable code checks can expose precision or speculative regressions hidden by a fluent answer. Coding also supplies realistic draft acceptance. | Use the official tests and declared pass@1 attempt policy; save code extraction, reasoning/output counts, timeouts and truncation. Fix evaluator runtime and resource limits. Use a common endpoint adapter or the custom-output evaluator, rather than allowing the harness to launch a different default engine. This is code generation, not a repository-agent score. [MB-LIVECODEBENCH](https://raw.githubusercontent.com/LiveCodeBench/LiveCodeBench/28fef95ea8c9f7a547c8329f2cd3d32b92c1fa24/README.md) |

Include the application's languages and ordinary/open-ended conversations in the service trace; a coding-only acceptance figure cannot predict their drafting cost. Optional repository-agent evaluation follows endpoint qualification and needs a fixed agent scaffold, tools and task budget as described in the shared guide.

## Run the experiments in this order

| ID | Controlled experiment and mechanism | Required observations and decision |
| --- | --- | --- |
| K01 — export and engine qualification | On one engine, qualify native target-only, then the NVIDIA export with equal effective cache/state settings and topology where supported. Separately compare engines on the **same** export. | Save resolved kernel/loader choices, module dtypes, load/repacking/graph peaks and scored text outputs. Check image quality for each qualified export. If effective paths cannot match, label a complete-configuration comparison. Reject unexpected fallbacks or task/protocol regressions before speed ranking. |
| K02 — recurrent state and prefix reuse | Replay the same sessions cold, with a repeated prefix, after eviction, and after a cancelled request. Interleave unrelated sessions and prefixes sharing text but differing in image or tool content. Exercise prefixes on both sides of the installed cache-match boundary. | Compare task outcomes and subsequent-turn state with a clean recomputation. Record KDA state slots, convolution/snapshot allocation, MLA cache occupancy, prefix hits and eviction. Reuse must not introduce another session's content or change tool state. A low-load pass alone does not qualify saturated pools. |
| K03 — DCP and pool allocation | Compare documented TP8 without DCP against TP8/DCP8 target-only, then adjust the state-to-KV allocation in separate runs using measured demand. Keep dtype and admitted work fixed where possible. | Log per-rank cache/state capacity, actual backend changes, communication time, admission stalls and peak memory. DCP shards target MLA KV; it does not imply every allocation is divided by eight. A capacity gain is useful only if quality and service objectives pass. |
| K04 — natural DSpark and rollback | Within a qualified topology, compare no draft with the matching draft at its documented default. Sweep 3/5/7 proposals only where that exact implementation supports them. Change ReplaySSM policy separately where both paths are supported. | Measure native acceptance distribution, its denominator, draft and verification time, extra memory, TTFT, first-final-answer latency and end-to-end task success. Include EOS/stop inside a proposed block, rejection, cancellation, eviction and the next request. If a matched off/on control cannot run, report a complete-stack comparison rather than a DSpark-only speedup. |
| K05 — cache/state precision | After K01–K04 qualify, vary supported MLA KV precision; separately vary KDA state precision with the target export fixed. | Repeat long-context and reuse quality strata and record actual kernels. A smaller state dtype can also switch the verification kernel, so report that interaction. Reject a memory saving that exceeds any declared task-regression limit. |
| K06 — mixed load and scheduling | Replay the frozen short/long/tool workload under the qualified configuration. Vary one supported admission, chunked-prefill or graph setting at a time, then confirm selected combinations. | Measure offered/completed load, queue delay, p95/p99 latency, failures, task success and full-node goodput. Confirm the selected candidate on held-out sessions with cache churn; include cold/warm startup if it affects the deployment decision. |

The current SGLang DSpark profile adds **DCP8 and ReplaySSM as well as drafting** to its target-only profile. Those two files alone cannot isolate speculative speedup. Build the supported target-only DCP control in the run manifest first, and retain any automatic backend changes. The cookbook's pool model separates KDA state, target MLA KV and replicated RadixArk draft KV; check actual allocator diagnostics instead of inferring capacity from weight size or the illustrative 414 MiB state matrix. DCP also has a documented symmetric-memory restriction. [kimi-k3-GR](https://docs.sglang.io/cookbook/autoregressive/Moonshotai/Kimi-K3), [architecture memory explanation](architecture.md), [DSpark audit](dspark.md).

The current cookbook also names a separate DFLASH route using `modal-labs/Kimi-K3-DFlash`, with block size 8, validation limited to Blackwell and no pipeline parallelism or DP-attention support. Treat this as a deferred candidate: it has no audited atlas artifact/profile. Pin and audit its draft revision, target/export compatibility and exact engine build before adding a matched target-only versus DFLASH experiment. Reuse K04's natural-acceptance and rollback checks; the cookbook description does not establish a local quality or speed result. [kimi-k3-GR](https://docs.sglang.io/cookbook/autoregressive/Moonshotai/Kimi-K3).

### Length, load and reasoning budget

Start with 4K, 16K and 32K **serialized input** buckets at concurrency 1 and 8, then 32 and an offered-rate ladder around saturation. Here K means 1,024 tokens. The current 65,536-token cap must cover input, retained history, tool/image tokens and the reserved output together. A nominal 64K input plus generation is infeasible; record it as such or choose a smaller near-cap input explicitly. Qualify a raised cap before 64K/128K input tests, and qualify those before any 1M attempt.

Use 128/1,024 output-token shape tests only to diagnose prefill/decode interference. They may truncate Kimi's reasoning and therefore do not establish answer quality. For the quality suites, predeclare a sufficient budget from a separate pilot, keep effort and sampling fixed for A/B, and report budget exhaustion and time to a useful final answer. Compare low/high/max effort as a separate application tradeoff, not as an engine speed difference. Do not force output length or use simulated acceptance in natural DSpark runs.

## Interpret published claims and produce a decision

Moonshot's benchmark table uses its stated effort, sampling, tools and harnesses. NVIDIA's native-versus-mixed-export table is publisher evidence, not a local threshold or proof of parity. The SGLang B300 DSpark speed rows use simulated acceptance; the two draft cards define their acceptance measurements differently. None supplies this campaign's natural acceptance or eight-B300 goodput. Inferact's hardware-count/TP16 wording still needs clarification. [Base card](https://huggingface.co/moonshotai/Kimi-K3/blob/f831ab66814297da540d832a5235f8e904f29d06/README.md), [NVIDIA card](https://huggingface.co/nvidia/Kimi-K3-NVFP4/blob/b2428a0b83a8b712ff2e1a8448a103d4175341f1/README.md), [DSpark evidence](dspark.md).

Produce one decision row per export/topology/draft tuple with artifact identities, per-suite and critical-stratum scores, paired uncertainty, raw response/tool traces, truncation/error counts, acceptance counters, peak memory and latency/goodput at each load. An answer-retaining evaluator is required: the atlas streaming probe checks completion but does not retain answers for scoring. Promote only when predeclared quality and service limits pass; reject a demonstrated regression; mark unsupported paths blocked and unresolved comparisons inconclusive. Preserve failures and the baseline for rollback. No production SLA or numerical quality margin is supplied by this plan.

Exact OEM topology; all-FP8 artifact availability; image/kernel/patch provenance; usable long-context concurrency; native-versus-NVFP4 quality; natural DSpark acceptance. Inferact’s peak card also needs clarification of its hardware-count versus TP16 wording.
