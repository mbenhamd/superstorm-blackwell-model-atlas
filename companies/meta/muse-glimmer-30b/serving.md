**Previous atlas baselines.** Support also exists at the previous stable baselines, vLLM v0.32.0 (`5df63a72…`) and SGLang v0.5.22 (`baa9befa…`). This follows from the release ancestry above and was confirmed by retrieving the model sources at those commits. The v0.32.0 registry maps the target and the DFlash assistant exactly as v0.33.0 does. Its `muse_glimmer.py` differs from v0.33.0 in multimodal input processing: v0.32.0 uses an in-tree `MuseGlimmerProcessor` with per-image pixel tensors, while v0.33.0 uses the Transformers `MuseGlimmerProcessor` with flattened patches and `image_grid_thw`. SGLang v0.5.22 has the same text-attention and KV-head/TP checks as v0.5.23. Its diff to v0.5.23 is confined to the vision path: v0.5.22 sizes vision attention from `hidden_size // num_attention_heads` (1536 / 16 = 96), while v0.5.23 reads a vision `head_dim` attribute, pads the projector width through `padded_projector_hidden_size`, and uses a different multimodal token-padding helper. The pinned base config sets no vision `head_dim`, and the SGLang config class that resolves these attributes was not compared across the two tags. These diffs were read, not executed; their effect on image inputs is unmeasured. [muse-glimmer-30b-V032-REGISTRY](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/model_executor/models/registry.py) [muse-glimmer-30b-V032-MODEL](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/model_executor/models/muse_glimmer.py) [muse-glimmer-30b-S0522-MODEL](https://raw.githubusercontent.com/sgl-project/sglang/baa9befa381511cd4d56f83980951e5a45fffc6d/python/sglang/srt/models/muse_glimmer.py)

**Recipe statements that v0.33.0 may have changed (verify, do not assume):**

- The recipe's `--max-num-seqs 32` rationale ("DFlash uses 16 query positions per active request… within vLLM's token budget") predates v0.33.0 #59468, which stops reserving DFlash/DSpark draft slots in the token budget. Test 32 against 64 with DFlash on the exact image.
- v0.33.0 adds opt-in XPress refinement for block-diffusion drafters (#54448) and FLy lossy verification (#53987). FLy deliberately accepts non-target tokens, so it is **excluded** from any quality-controlled configuration. XPress has no Muse-specific evidence.

The PR numbers above are taken from the v0.33.0 release body. This page did not inspect those PRs' code for Muse-specific behavior. [muse-glimmer-30b-V-LATEST](https://api.github.com/repos/vllm-project/vllm/releases/latest)

**DFlash fixed draft length.** The recipe explains `num_speculative_tokens: 15` as `block_size 16` minus the slot that re-presents the last accepted token. The publisher's speedups (3.1× on RTX 5090 via llama.cpp, 1.5–1.8× on Apple via ExecuTorch, batch 1, greedy) are consumer-device measurements. They do not predict B300 batched behavior. At high concurrency, verifying 16-token blocks competes with useful decode work. SGLang's DFlash regression test checks GSM8K accuracy (threshold 0.85 on 200 examples) and acceptance length (threshold 2.5; author-measured median 3.12 at block size 5, batch 1/4/8, 512/256 tokens). Accuracy cannot detect a broken draft, because target verification keeps answers target-identical; the test's docstring states that the accuracy threshold alone would not have caught the documented bugs. Acceptance length is therefore the guard for draft integrity. PR #37510 reports GSM8K 0.965 and a mean acceptance length of 5.25 on one B200 with the NVIDIA export plus FP8 draft, using older revisions of both (`f45fad56`, `e8192f3a`). These are author measurements, not reproduced. [muse-glimmer-30b-S-PR37510](https://api.github.com/repos/sgl-project/sglang/pulls/37510)

## Side-by-side first candidates (unbenchmarked)

| Option | Expected benefit | Cost / risk | Reject if |
| --- | --- | --- | --- |
| vLLM TP1 BF16 ×8, target-only | Quality reference; no collectives; full multimodal | 59.55 GB serialized weights per GPU; ~53.0 GB of decoder weights streamed per decode step (derived) | Tool/reasoning parsing fails on the pinned template |
| + DFlash assistant (BF16 or FP8 draft) | Fewer target forward passes per accepted token at low concurrency | ~5.11 GB extra (BF16), extra KV and verify compute; acceptance depends on the layer-index convention | Mean acceptance near 1, or goodput at the target concurrency falls below target-only |

## KServe integration

KServe is the required control plane; its installed version, resource kind and runtime integration are unknown. Two layouts fit: one `InferenceService` per GPU (eight TP1 predictors), or a single predictor scaled to eight 1-GPU replicas. Under either, engine arguments are passed through the ServingRuntime or predictor container args. KServe does not substitute for engine-level DP: cross-replica prefix-cache affinity for long agent sessions needs routing above the engine. Model-cache volume and image digest pinning apply as for other families. Upstream KServe references do not identify the installed cluster.

## Measurements still required

1. The effective attention backend and sliding-window eviction on SM103 in each engine image.
2. KV tokens available at TP1 versus TP2 with BF16 and FP8 KV.
3. DFlash acceptance length on agent traces, compared with GSM8K.
4. Tool-call and reasoning-channel correctness with the pinned base template versus the superseded template bundled by the NVIDIA, Red Hat and Inferact exports.
5. Prefill and decode throughput for BF16, FP8-block and NVFP4 variants at the same concurrency and SLO.
6. Image input accuracy on BF16 versus each export that retains vision.

The [benchmark decision criteria](../../../reports/optimization.md#benchmark-decisions-and-measurement-contract) define common controls. No result on this page is a measured B300 result.
