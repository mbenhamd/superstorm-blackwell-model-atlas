## Decision and applicability

**Proposed experiments; no GPU results.** Select the export and GPU grouping for a text/image service with a measured quality floor. Gemma's 50 sliding-attention layers, ten global layers, tied embeddings/head and final logit soft-cap require more specific checks than a uniform dense-transformer throughput sweep. The base and both Red Hat current cards/configs matched the atlas pins on 2026-10-15 UTC. [gemma-4-31b-it-CFG](https://huggingface.co/google/gemma-4-31B-it/raw/842da3794eaa0b77d5f08bae87a17459d91ff475/config.json), [architecture](architecture.md).

Start with [vLLM BF16 TP1](../../../profiles/gemma-4-31b-it.bf16.vllm.baseline.json), then the pinned [FP8](../../../profiles/gemma-4-31b-it.fp8.vllm.baseline.json) and [NVFP4](../../../profiles/gemma-4-31b-it.nvfp4.vllm.baseline.json) exports. The [SGLang NVFP4 profile](../../../profiles/gemma-4-31b-it.nvfp4.sglang.baseline.json) remains an exact-export compatibility probe. Require evidence that the selected build handles compressed-tensors block FP8 or packed NVFP4, as applicable, before timing. Resolve effective KV dtype rather than inferring it from weight precision. The exports preserve some components at higher precision; their file-size ratios do not predict GPU-memory or speed ratios. [precision](precision.md).

The supplied profiles allow 32,768 total tokens and 32 active requests. Screen 4K/16K serialized inputs with 128/1,024 output-token budgets at concurrency 1 and 8, then 32 if qualified. Account for image and template tokens. Longer contexts, larger batches and additional replicas require separate capacity checks. Audio is excluded for this variant (`audio_config: null`); a generic family example does not qualify it. The profiles intentionally omit automatic tools: pin the Gemma template/parser and verify its behavior before tool evaluation. No matching drafter is identified in these profiles, so a speculative-decoding claim for another Gemma variant is not an experiment ready to run here. [gemma-4-31b-it-CARD](https://huggingface.co/google/gemma-4-31B-it/raw/842da3794eaa0b77d5f08bae87a17459d91ff475/README.md).

## Architecture and export experiments

| ID / hypothesis | Controlled experiment | Evidence and decision |
| --- | --- | --- |
| G31-01 — Text quantization retains useful text and image quality. | Compare BF16, block FP8 and NVFP4 in one qualified vLLM build at TP1 and matched KV dtype, cache policy, mode and batch. Verify loaded exclusions, tied embedding/head handling and the configured soft-cap; compare finite outputs with the publisher reference. Repeat the same export in SGLang only after its load gate. | Save effective module/backend diagnostics, startup/repacking peak, steady memory and task-specific quality deltas. Report text and multimodal results separately: keeping vision weights at higher precision does not guarantee image-conditioned language quality. Stop on loader mismatches, unintended fallback or quality failure. |
| G31-02 — Sliding/global attention remains correct across cache boundaries. | Place known facts just inside and outside the 1,024-token local window and at early/middle/late positions in longer prompts. Compare cold prefill, chunked prefill and warm-prefix replay where supported. Add divergent suffixes, eviction, batch-size changes and cancellation, then replay from a fresh session. | Collect local/global pool occupancy, allocator block sizes, evictions and task-by-position accuracy. Facts outside the local window still have a global path; distinguish ordinary model errors from a repeatable cache-policy regression against the fresh reference. Do not infer physical K/V buffer sharing solely from `attention_k_eq_v`. |
| G31-03 — Document resolution buys enough accuracy to justify its cost. | Freeze processor revision, source image bytes, aspect ratio handling and prompt. Start with one page; vary page count and resolution in separate experiments within the verified processor limits. Repeat identical text with different images and reversed page order. Add ordered video-frame inputs only after that exact processor/runtime path qualifies. | Report text/table/formula errors, visual-token counts, preprocessing/encoder time where available, TTFT, peak memory and completion failures. Missing/reordered images or reused results from another image reject the path. Document accuracy cannot establish temporal-video accuracy, and frame input does not qualify an arbitrary video API. |
| G31-04 — Thinking and tool handling preserve the user-visible contract. | Freeze thinking on/off within each export/engine A/B, with explicit output budgets and sampling. Separately compare thinking policies on identical tasks. After parser qualification, test no-call, single-call, multiple-call and multi-turn tool results, including streaming boundaries and cancellations. | Save parsed reasoning, final answers and tool calls with their raw streams. Measure first-answer latency and task correctness, not only TTFT or valid JSON. A malformed parser output is a protocol failure; a well-formed wrong function is a quality failure. |
| G31-05 — Replicas improve node capacity more than tensor sharding. | Compare eight TP1 replicas, four TP2 groups and two TP4 groups on the same eight GPUs for the same qualified export. Reuse an arrival trace containing short chat, long documents and image requests, with fixed routing/cache affinity and CPU resources. Fix total-node admission/concurrency and log per-group batching/scheduler limits before separate capacity tuning. | Report whole-node goodput under declared latency/quality requirements, tails, per-GPU peak/headroom and burst recovery. Changed admission or batching policies require a complete-configuration comparison. Keep single-group latency separate. If image preprocessing saturates CPU or a global cache pool fills first, document that bottleneck before changing TP. |

The source configuration motivates these cases; the expected performance outcome remains unknown. Lower precision, more replicas and a larger window are choices to evaluate independently before interaction testing. [gemma-4-31b-it-CFG](https://huggingface.co/google/gemma-4-31B-it/raw/842da3794eaa0b77d5f08bae87a17459d91ff475/config.json), [serving](serving.md).

## Quality tasks chosen for this model

| Task and primary source | Why it belongs here / controls and outputs |
| --- | --- |
| [OmniDocBench v1.5](https://github.com/opendatalab/OmniDocBench/tree/v1_5) — MBENCH-OMNIDOC-V15 | Document parsing directly exercises variable-resolution vision and long generated structure. Pin the v1.5 code and matching dataset revisions, image policy, prompt and matching configuration. Report text/read-order edit distance, table TEDS and formula CDM separately. The publisher names v1.5; current main has later revisions. Its stated average edit distance is not interchangeable with the benchmark's composite overall score. |
| [MMMU-Pro](https://github.com/MMMU-Benchmark/MMMU/tree/main/mmmu-pro) — MBENCH-MMMUPRO | Use a fixed standard or vision setting to check image-dependent reasoning beyond transcription. Preserve image-placeholder order and pin prompt mode; report per-subject accuracy and failures. This complements document parsing because correct OCR can still lead to a wrong answer. |
| [RULER v1](https://github.com/NVIDIA/RULER/tree/rulerv1-ns) — MBENCH-RULER-V1 | Use fixed generated retrieval, tracing and aggregation tasks to examine the local/global attention tradeoff at feasible lengths. Pin both its driver and linked NeMo-Skills implementation; report per-task/length scores. Keep the custom 1,024-token boundary probes outside the standard benchmark aggregate. |
| [LiveCodeBench](https://github.com/LiveCodeBench/LiveCodeBench) — MBENCH-LCB | A frozen `release_v6` or declared date window gives executable checks of thinking and quantization during long code generation. Pin evaluator limits, prompt adapter and samples per problem; report pass@1, truncation and runtime errors. This tests coding quality, without establishing an agent's repository-editing success. |
| [BFCL](https://github.com/ShishirPatil/gorilla/tree/main/berkeley-function-call-leaderboard) — MBENCH-BFCL | Use declared offline single/multi-turn categories only after the Gemma parser/template gate. Measure selected function and arguments, including no-call cases. Record the handler and tool environment; schema-valid output alone is insufficient, and subset scores are not overall BFCL scores. |
| Held-out application documents and conversations | Include the actual languages, layouts, page counts and output formats, plus answerable and unanswerable questions with fixed scoring rubrics. These establish relevance to the service. Add temporal frame questions only if that path is deployed; exclude audio. |

These are local recommendations based on coverage of likely failure modes. The publisher's benchmark table is a set of reported quality results, not a reproduced B300 result or an acceptance floor for Red Hat exports. Freeze item IDs before evaluation, retain a separate tuning set and label any screening subset. A different benchmark version, parser, image budget or thinking policy creates a new comparison. [gemma-4-31b-it-CARD](https://huggingface.co/google/gemma-4-31B-it/raw/842da3794eaa0b77d5f08bae87a17459d91ff475/README.md).
