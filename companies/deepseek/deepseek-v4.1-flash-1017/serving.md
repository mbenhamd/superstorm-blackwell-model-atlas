**Constraints and checks.**

- **Reasoning defaults (Source).** At v0.32.0 and main `aa4022dc`, the Python `deepseek_v41` tokenizer turns thinking **on** when neither `thinking` nor `enable_thinking` is sent, and the Rust V4.1 renderer (the recipe's default frontend) falls back to enabled `high`; both map `low`/`high`/`xhigh`/`max` to 50/75/75/100 with default `high` (75), matching the publisher's `encoding.py` (`low` 50, `high` 75, `max` 100). The recipe guide's prose (25/50/75/100, default 50) contradicts both; use the source mapping and send an explicit integer effort for comparisons. - **KV-cache layout differs by backend (Source).** With `FLASHINFER_MLA_SPARSE_DSV41` on SM10x, `fp8` is a per-tensor FP8 layout; with `FLASHMLA_MEGA_ATTN_DSV41`, `fp8` aliases `fp8_ds_mla` and only `nvfp4_ds_mla` (also the backend's resolution of an unspecific dtype) stores the publisher's FP4 compressed cache. Both are SM100-family code paths; SM103 membership is asserted by the capability-family check, not by a B300 run. See [precision](precision.md#interpretation).
- **Indexer logits buffer (Recipe + Derived).** The recipe states the sparse indexer allocates `max-num-batched-tokens × max-model-len × 2` bytes at startup. With the B300 cell's 8,192 batched tokens and the default 1,048,576 `max-model-len`, that is 16 GiB per rank. Lowering `--max-model-len` for workloads that do not need 1M reduces it proportionally.
- **Engram host memory (Source; Derived; Hypothesis).** In v0.32.0 and v0.33.0 `EngramConfig.cpu_offload` defaults to `true`, and when `--engram-config` is absent the engine constructs `EngramConfig()` for any model with Engram layers. Host offload is therefore the default for every vLLM topology here; HBM-resident tables require an explicit `{"cpu_offload":false}`. Each private host copy pins ≈183 GiB of FP8 tables (≈189 GiB with scales): four independent TP2 replicas pin ≈730–755 GiB and two TP4 replicas ≈366–378 GiB. With DP > 1, `dp_shared_memory` resolves on by default (offload on, no THP, no elastic EP); the DP ranks of one co-located deployment then share one copy through `/dev/shm` and a shared IPC namespace, so the DEP8 cell needs a pod `/dev/shm` of at least ≈189 GiB. If `/dev/shm` cannot hold the tables or the ranks are not co-located, the engine logs a warning and does not share; the resulting host footprint was not traced. Sharing does not apply across separate KServe pods, which each hold a copy. The node's RAM is not inventoried. Confirm the `Resolved Engram configuration` log line per engine. ## KServe integration (Hypothesis)

Each candidate is one KServe predictor per engine instance (TP2 or TP4) or one eight-GPU predictor (DEP8). Pin `--revision` and the tokenizer to `1bae0e108899`. Provide a shared, pre-populated model cache: four replicas each downloading ≈475 GiB is avoidable. Allow at least the recipe's 3,600 s readiness window plus first-boot kernel autotuning. Size pod memory for pinned Engram tables and `/dev/shm`. Verify which of these the installed KServe resource kind exposes before writing manifests. See [KServe](../../../frameworks/kserve/).

## Prompt and output protocol

The 1017 repository has no `chat_template.jinja`; prompts must go through the engine's V4.1 encoder (`--tokenizer-mode deepseek_v41` in vLLM; SGLang's `encoding_dsv41`) or DeepSeek's `deepseek-recipe` library. The unsuffixed V4.1 repository gained a `chat_template.jinja` through repository PR #68 (opened by a non-DeepSeek account); its effort map includes `medium` = 62, which the publisher `encoding.py` does not define. Do not copy that template into a 1017 deployment. Tool calls are DSML blocks; tool results return in `<tool_result>` tags. The 1017 card recommends `temperature=1.0`, `top_p=1.0`, `max_tokens` ≥ 256K. ## Optimization priorities (proposed experiments, not results)

1. **Correctness gate.** Exact 1017 revision, target-only, each engine: one text request, one image request (the vision path is separate), a multi-turn DSML tool exchange, an explicit-effort reasoning request, and cancellation/reuse. Record resolved backends, cache dtypes and Engram placement.
2. **Compressed-cache precision (vLLM DEP8).** `--kv-cache-dtype fp8` (recipe) versus `nvfp4_ds_mla` (publisher FP4 format) with `FLASHMLA_MEGA_ATTN_DSV41`. Mechanism: FP4 halves compressed-KV bytes and matches training; measure long-context retrieval quality (e.g. evidence just inside/outside the 128-token window and at 256K+), KV capacity and decode latency. Reject on quality loss.
3. **Replica shape.** Four TP2, two TP4 and one DEP8 at equal aggregate offered work; include host-memory footprint, `/dev/shm` use and startup time. At TP4, run Engram host (default) and resident (`cpu_offload:false`) as separate arms.
4. **DSpark.** Target-only versus k=5; adaptive verification `false` versus `true` at TP > 1. On v0.32.0/v0.33.0 the `true` arm needs `cudagraph_mode` `FULL_DECODE_ONLY` or a build containing #59986, because #59970 reports an illegal memory access with `FULL_AND_PIECEWISE`; run it with hang detection (PR 62769); natural acceptance on the actual workload (the SGLang cookbook expects lower acceptance on agentic traces and recommends no speculation at large batch).
5. **Bounded replay (SGLang).** On versus off for prompt-heavy agentic traffic; it changes numerics, so pair with quality checks. Keep results in the execution repository and use the [benchmark decision criteria](../../../reports/optimization.md#benchmark-decisions-and-measurement-contract).

## Remaining uncertainty

Release-image (not preview-image) support on SM103 for both engines; host RAM on the node; actual per-rank memory peaks; DSpark acceptance on target traffic; effect of FP8 versus FP4 compressed cache; NVFP4 export loadability in released engines; 1017-specific engine validation, which neither upstream recipe has yet published.
