## Decision and prerequisites

**Proposed campaign; no GPU results.** Choose a configuration for long multi-turn and image-bearing requests that preserves quality while balancing KDA state, sparse history and MoE work. The 34 recurrent KDA layers, 11 sparse-MLA layers, four mHC residual streams and vision encoder create different memory and correctness risks from GLM 5.3. The 136 MiB state-matrix illustration in [architecture](architecture.md) excludes convolution state, snapshots and runtime overhead; it cannot predict actual concurrency by itself. [glm-5.3-flash-CFG](https://huggingface.co/zai-org/GLM-5.3-Flash/raw/46a050bec13002ad29ee795c16e61cf4fa3c4a9c/config.json).

Planning evidence was refreshed on 2026-10-15 UTC (October 16 in Paris). Current publisher card/config bytes match the pinned base revision; all three current repository revisions match [model.json](model.json). Retain candidate/probe labels until real-weight checks pass. Record a complete [experiment manifest](../../../benchmarks/experiment.template.json) for each arm.

## Quality workloads and why they belong

Apply the [shared benchmark selection and evaluation rules](../../../benchmarks/MODEL-BENCHMARKS.md), including answer retention, paired quality uncertainty and task-specific thresholds. Start coding checks with its EvalPlus functional screen, then a frozen LiveCodeBench release/date range before any repository-agent campaign. Record pass@1 and evaluator failures with fixed language/runtime and budgets; this catches code regressions without letting tool/scaffold differences dominate the first export comparison.

| Workload | Proposed evaluation and rationale | Report separately |
| --- | --- | --- |
| Long-context state | Pin RULER v1 and its NeMo-Skills dependency; select retrieval, variable-tracking and aggregation tasks at several lengths. Reuse the exact tokenized payloads for cold, warm-prefix and post-eviction runs. Add held-out multi-turn document questions requiring early and late evidence. | Scores by task, length and evidence position, plus contamination between interleaved sessions. RULER is a synthetic diagnostic, not proof of 1M-context application quality. [MBENCH-RULER-V1](https://raw.githubusercontent.com/NVIDIA/RULER/rulerv1-ns/README.md), [MBENCH-RULER](https://github.com/NVIDIA/RULER). |
| Image/document understanding | Use a fixed DocVQA single-document validation set and official ANLS scoring. Freeze image bytes, resize policy, processor revision and answer extraction. Add local two-image questions and image-bearing follow-ups with checked answers. | ANLS, wrong-document answers, visual tokens, preprocessing/encoder time and peak memory. Local multi-image cases are a separate regression set, not a DocVQA score. Video requires its own frame/timestamp and quality campaign. [MBENCH-DOCVQA](https://www.docvqa.org/datasets/docvqa), [MBENCH-DOCVQA-EVAL](https://rrc.cvc.uab.es/?ch=17&com=tasks). |

| Coding service, if required | Run a frozen SWE-bench Verified campaign with identical agent/tools, task images and budgets across exports. [MBENCH-SWEBENCH](https://www.swebench.com/SWE-bench/). |

The RedHat card publishes selected reasoning scores without a paired official-FP8 table. Re-evaluate FP8 and NVFP4 under identical conditions; the card cannot establish retained multimodal quality or a permitted regression. ## Ordered experiments

| ID | Controlled comparison and mechanism | Measurements and decision |
| --- | --- | --- |
| G53F-01: load and precision | Qualify target-only official FP8 on each engine/build. Then compare RedHat NVFP4 on the same vLLM build, topology, cache/state settings and payloads; qualify BF16 independently if needed. Separate stored checkpoint completeness from resident target/vision tensors and inventory any deliberate draft exclusions. | Save tensor-group/kernel diagnostics, load/repacking/graph peaks and per-task quality deltas. Missing tensors required by the target or enabled vision path, fallback surprises or image-processing failures block promotion. Documented target-only MTP omission is valid; check its loading in G53F-05. |
| G53F-02: KDA rollback | Compare the same logical request after fresh prefill, shared-prefix reuse, divergent suffixes, interleaved unrelated sessions, eviction and cancellation. Repeat around the engine's actual cache/chunk boundaries and four-token convolution/pooling neighborhoods. Test both one-shot and supported chunked prefill. | Record final task scores and available state/cache diagnostics; use reference logits within a declared tolerance where supported. Sampled text differences alone are not proof of corruption. Require correct continuation after cancellation and speculative rejection. Keep the configured KDA lower bound fixed. |
| G53F-03: pool balance | At fixed total memory reservation, compare the baseline state/KV split with one candidate derived from boot-log pool sizes and the intended request-length/concurrency distribution. Repeat with short many-session traffic and long few-session traffic. | Record actual state slots, snapshots, KV tokens, startup-clamped concurrency, pool exhaustion, eviction and goodput. Promote only when both pools retain the declared reserve; enlarging state at the expense of long-request capacity is not a universal improvement. |
| G53F-04: cache/backend pair | On the same SGLang image and TP4 layout, compare the two qualified KV/DSA pairs. Hold weights, state dtype, speculation and offered traffic fixed. Re-run the long-context and image quality gates. | Report memory capacity, sparse-prefill/decode time, TTFT, first-answer latency and goodput as a pair comparison. Diagnose regressions with profiling; do not attribute all gains to FP8 alone. |
| G53F-05: MTP | Compare target-only with the [SGLang native-MTP candidate](../../../profiles/glm-5.3-flash.fp8.sglang.mtp.json), then supported depths 1/3/5. Record steps, top-k and draft-token count separately; the existing candidate is 5/1/6. Qualify vLLM and RedHat/MTP separately, requiring the speculative arm's MTP tensors, scales and effective precision to load correctly. | Record natural accepted length, rejected-branch restoration of KDA/convolution state, DSA cache commits, draft/verification time, memory and quality. Test low load, sustained batches, EOS and cancellation. Stop if state corruption appears even with attractive acceptance. |
| G53F-06: eight-GPU layout | Qualify TP8; compare one TP8 group with two disjoint TP4 replicas under the same node workload. Only if prefill interference is material, investigate a 4+4 prefill/decode layout as a separate candidate. | Record whole-node goodput, queueing and communication. Require correct KV plus KDA state transfer and recovery; match layouts/dtypes on both roles and qualify the exact connector and MoE runner. Match the MoE runner across colocated/split arms where supported; otherwise disclose a combined backend/PD comparison. Include transfer/router costs. |

The inspected vLLM target loader deliberately skips speculative layers. Record this exclusion rather than treating stored MTP tensors as mandatory target-only residents; confirm the same behavior for the selected image. [MBENCH-GLM53F-TARGET-LOADER](https://raw.githubusercontent.com/vllm-project/vllm/f8460ef23659afd69046a81529ec2295e4c3f686/vllm/models/glm5next/common/model.py).

Use complete serialized input buckets of 4,096, 16,384, 32,768 and 61,440 tokens with 128/1,024 output caps; add 4,096-input/8,192-output reasoning requests. Keep text and image-bearing traffic as separately reported strata, counting visual and template tokens within the 65,536 cap. Screen at concurrency 1 and 8, then 32 and a pilot-derived offered-rate ladder. Replay a fixed mixture of long image/document prefill and ongoing short decodes to expose interference. These shape caps do not define the quality evaluator's answer budget.

## Required outputs and promotion

Deliver manifests, raw responses and parser outputs, quality scores by modality/task/length, per-rank memory with separate state/KV pools, natural-acceptance distributions and the offered/completed traffic trace. Attach a decision table for each experiment with the [protocol's](../../../benchmarks/PROTOCOL.md) repeated randomized A/B analysis and declared quality, latency, error, capacity and useful-improvement thresholds. The [client result schema](../../../benchmarks/result.schema.json) alone does not capture hybrid-state correctness or model quality.

Reject stale-state behavior, failed multimodal quality gates or a transfer path without real-weight correctness evidence. A preview that cannot qualify stays blocked for performance comparison; it is not assigned a zero-throughput result. A credible speedup must meet the declared threshold with uncertainty accounted for and survive cancellation, eviction and burst recovery. No production SLA or winning configuration is supplied by this plan.
