# vLLM v0.32.0: B300 upgrade and experiment priorities

**Source review: October 18, 2026.** v0.32.0 was released at 06:50:48 UTC, with tag commit `5df63a7203cdb9328d824a27b682e77c7b9928be`. This analysis compares selected implementation paths with v0.31.0 (`db9527a46873454610df6dbedf79a36d6bf1a7f6`) for the eight catalog families on one 8×B300 node. KServe remains the required deployment layer. No engine, model payload or B300 experiment was run. [V032-RELEASE](https://api.github.com/repos/vllm-project/vllm/releases/tags/v0.32.0), [V032-TAG](https://api.github.com/repos/vllm-project/vllm/git/ref/tags/v0.32.0).

The first comparison should change the **engine image while retaining model, tokenizer, draft, topology, explicit precision, request contents and workload**. Then evaluate one relevant new mechanism at a time. Defaults can change across releases: identical command lines do not necessarily produce identical cache formats or kernels. Record resolved settings before interpreting a gain.

It cannot be mixed with a different named reasoning/tool parser. A template field's existence alone does not qualify its streaming semantics or the complete export. Retain the model-specific parser until this exact tokenizer/template pairing is checked. [V032-R-PARSER-MANAGER](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/parser/parser_manager.py), [V032-R-RESPONSE-TEMPLATE](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/parser/response_template.py).

| Family | Highest-value new comparison | Keep separate |

### Qwen 3.8 27B

**New mechanism:** PR #56050 lets the optimization predicate recognize NVFP4 layers inside `modelopt_mixed`. The NVIDIA export can consequently use eligible activation-quantization fusion. Mixed checkpoint loading was already supported in v0.31; this is an optimization-selection correction. Start with the retained NVIDIA revision, TP1, FlashInfer/BF16 KV and matching admission/batching. Keep compilation enabled and inspect effective fusion; eager execution or disabled passes can bypass the proposed benefit. The PR's performance example is a different derivative on SM121, so it supplies no B300 speed estimate. [V032-H-MODEL-CONFIG](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/config/model.py), [V032-H-PR-56050](https://github.com/vllm-project/vllm/pull/56050).

**Follow-up:** compare official FP8 and NVIDIA mixed weights at the same KV precision; then FlashInfer/FP8 KV, FA4/BF16 KV and native MTP1/2/3 independently. The hd256 FA4/quantized-KV restriction is unchanged. Native MTP requires its matching revision; tokenization, output-head quantization and GDN state remain separate controls. GDN's zero-draft-state fix chiefly enables correct transitions when ngram produces no draft; it is not proof that an always-drafting MTP problem was resolved. [V032-H-FAUTIL](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/v1/attention/backends/fa_utils.py), [V032-H-GDN](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/v1/attention/backends/gdn_attn.py), [V032-H-PR-56531](https://github.com/vllm-project/vllm/pull/56531).

### Qwen 3.8 Flash Next

**New mechanism:** merged QSA projections and fused preparation reduce GEMM launches and intermediate work. The merged TP4 shape has an SM103 plan; the separate #59214 addition targets exact SM100/B200 plans, while SM103 already had plans in v0.31. These paths require eligible shapes and precision; they do not turn quantized experts into the same BF16 GEMM. Compare the official FP8 TP4+EP configuration across releases first. Projection fusion is normally automatic without LoRA. [V032-H-QSA](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/models/qwen4_exp/nvidia/qsa.py), [V032-H-LLGEMM](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/models/qwen4_exp/nvidia/low_latency_gemm.py).

**Next explicit change:** `--enable-hc-sp` distributes HC/PLE work at TP>1, with additional communication. It requires a compatible CUDA/PP1/model path; existing MoE sequence parallelism can also activate it. Compare resolved off/on behavior at fixed TP4, for long prefill and short-turn decode separately. The projection PR's GB300 BF16 kernel ratios were much larger than its whole-serving changes; neither establishes the exact FP8 export's gain. Preserve the difference between two independent TP4+EP4 KServe groups and one TP4×DP2 expert world of eight. [V032-H-PR-56322](https://github.com/vllm-project/vllm/pull/56322), [V032-H-PR-59533](https://github.com/vllm-project/vllm/pull/59533).

NIXL's PLE page-length correction matters when P/D transfer and MTP are actually used. It does not justify disaggregating the eight-GPU node by itself. Main KV, indexer KV, PLE/convolution state and MTP still need distinct accounting. [V032-H-NIXL](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/distributed/kv_transfer/kv_connector/v1/nixl/base_worker.py).

**Draft-cache precision:** #60023 makes QSA honor numeric `--kv-cache-dtype-skip-layers` indices. The retained Flash Next config has 48 target layers and one MTP layer at index 48. With a supported MTP setup, compare `--kv-cache-dtype fp8` against the same setting plus `--kv-cache-dtype-skip-layers 48`: the latter retains FP8 target KV and resolves the draft KV to BF16. This does not change indexer-cache or PLE-state precision. Record resolved cache dtypes, natural acceptance, draft memory and request latency; the PR's GB10 result on another NVFP4 revision is not a B300 prediction. [V032-H-QSA](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/models/qwen4_exp/nvidia/qsa.py), [V032-R-QWEN-MTP](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/models/qwen4_exp/nvidia/mtp.py), [V032-R-ENGINE-ARGS](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/engine/arg_utils.py).

### Changes shared by both Qwen families

**Image/video preprocessing:** the inherited Qwen vision implementation now supports device-side normalization. The ordinary Python/native-model path enables it by default for these families; the Rust frontend forces it off. Compare the resolved `mm_device_do_normalize` setting with pinned processor parameters and identical media. Measure CPU preprocessing, host-to-device transfer and encoder time, with output parity. The uint8 transfer and GPU normalization path provides no text-decoder speed claim. [V032-R-QWEN-VL](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/model_executor/models/qwen3_vl.py), [V032-R-QWEN35](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/model_executor/models/qwen3_5.py), [V032-H-MODEL-CONFIG](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/config/model.py).

**Rotary-table memory:** without video pruning, the M-RoPE position multiplier changes from 4 to 1; pruning retains 4 and drafts follow the target's pruning state. For the retained default-RoPE configs, `262144 × 64 × 2 bytes` gives a **32 MiB BF16 cos/sin table**, versus 128 MiB previously. The derived saving is 96 MiB per shared cached table, not per attention layer or a fourfold reduction in total model memory. `get_rope` reuses cached objects; count actual allocations. Extended/YaRN configurations need their own positional-quality check. [V032-R-QWEN-VL](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/model_executor/models/qwen3_vl.py), [V032-R-MROPE](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/model_executor/layers/rotary_embedding/mrope.py), [V032-R-ROPE-CACHE](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/model_executor/layers/rotary_embedding/__init__.py).

### Kimi K3

**New mechanism:** packed speculative KDA fuses convolution, recurrent update and output normalization. After DSpark is enabled, `additional_config.kda_spec_decode_backend=auto` selects it only when eligible. Compare `native` versus `flashinfer` at fixed proposal depth and state dtype; a forced unsupported FlashInfer path raises. Requirements include SM10x, the callable packed kernel, supported local heads (TP8 gives 12), dimension128, convolution width4, 1–7 proposals, BF16 inputs/convolution state, FP32 or BF16 recurrent state, bounded negative gate, SD state layout and RecoverSSM disabled. Batches containing prefill or ordinary non-speculative decode rows do not use this pure-speculative path. [V032-KM-KDA](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/models/kimi_k3/nvidia/kda.py), [V032-KM-PR54255](https://github.com/vllm-project/vllm/pull/54255).

Start with native MXFP4 TP8 and the pinned Inferact DSpark, using natural acceptance and identical reasoning/tool workloads. BF16 versus FP32 recurrent state is a separate quality/capacity experiment. The upstream B300 evaluation used a different target/build, so it does not qualify this release artifact. For long context, compare fixed DCP layouts across releases to isolate the new fused K/V packing; then compare DCP degrees for whole-request latency. [V032-KM-MLA](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/models/kimi_k3/nvidia/mla.py), [V032-KM-PR56881](https://github.com/vllm-project/vllm/pull/56881).

**Exclusions:** the reported 20→4 DSpark cache-group recovery concerns ROCm grouping, not NVIDIA. `latency_specialized` remains absent from v0.32 and present only in the separately inspected main path. DeepEPv2 shared-expert sharding needs `VLLM_KIMI_K3_SHARD_SP_SHARED_EXPERT=1` and the model's sequence-parallel gates; plain TP8/DP1 with DeepEPv2 does not activate them. NVIDIA mixed-export qualification remains separate, and its historical bundled patch is not a drop-in release patch. [V032-KM-PR59733](https://github.com/vllm-project/vllm/pull/59733), [V032-KM-MAIN-SPECIALIZED](https://raw.githubusercontent.com/vllm-project/vllm/371745ebd6c12f314402c6c319de2e7ef82c2981/vllm/models/kimi_k3/nvidia/specialized_decode/runtime/__init__.py), [V032-KM-MODEL](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/models/kimi_k3/nvidia/model.py), [Q31-CAT-KIMI-NV-SITECUSTOMIZE-PY](https://huggingface.co/nvidia/Kimi-K3-NVFP4/raw/b2428a0b83a8b712ff2e1a8448a103d4175341f1/runtime_patches/sitecustomize.py).

### GLM 5.3

**New default:** `GlmMoeDsaForCausalLM` changes `auto` KV to FP8 E4M3 on CUDA capability family10, which includes B300/SM103. This hook is not conditional on FP8 target weights and does not apply to GLM Flash. Explicit FP8 configurations already made this choice; their memory savings cannot be counted again as a release gain. Compare explicit BF16/FP8 KV with long-context quality and latency, then existing TP8 versus independent TP4 groups and MTP1/3/5. [SP32-SRC-vllm-model_executor-models-config-py](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/model_executor/models/config.py), [SP32-SRC-vllm-platforms-interface-py](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/platforms/interface.py).

**Avoid false attribution:** the headline sparse-index conversion improvement is in the FA3 sparse backend, whose final gate is capability major9, BF16/FP16 KV and no DCP. The fused draft metadata headline likewise does not establish a gain on B300's default FlashInfer/FlashMLA sparse path; these builders do not advertise the required update support. Check the actual metadata fallback before interpreting a speculation gain. [SP32-SRC-vllm-v1-attention-backends-mla-flashattn_mla_sparse-py](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/v1/attention/backends/mla/flashattn_mla_sparse.py), [SP32-SRC-vllm-v1-attention-backends-mla-flashinfer_mla_sparse-py](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/v1/attention/backends/mla/flashinfer_mla_sparse.py), [SP32-SRC-vllm-v1-worker-gpu-spec_decode-speculator-py](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/v1/worker/gpu/spec_decode/speculator.py).

Long-prefill row sharding is worth considering only when the scheduled batch is large enough: at least `16,384×TP` query rows, with additional topology/graph guards. An 8192 batching budget never triggers it at TP4. Large budgets trade staging memory and fairness for prefill compute savings. Above 262144 configured context, the new sparse-workspace factor defaults to2 rather than5; compare memory against extra gather passes, where that helper is used. HiSparse remains a conditional offload/capacity experiment with a resident-serving control, not a default speed recommendation. [SP32-SRC-vllm-v1-attention-backends-mla-indexer-py](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/v1/attention/backends/mla/indexer.py), [SP32-SRC-vllm-config-attention-py](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/config/attention.py), [SP32-PR-60083](https://api.github.com/repos/vllm-project/vllm/pulls/60083).

### GLM 5.3 Flash

**State precision:** `--mamba-ssm-cache-dtype bfloat16` is now honored by KDA layer and cache-spec construction; `auto` remains FP32. Compare explicit FP32 versus BF16 at fixed topology and speculation setting. BF16 halves recurrent-state tensor bytes, including recurrent checkpoint/rollback buffers where allocated. Convolution state and other workspaces do not necessarily shrink, so total request memory does not halve. Validate long-context quality, prefix branches, cancellation and speculative rollback before spending the saved capacity on concurrency. [SP32-SRC-vllm-models-glm5next-common-kda-py](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/models/glm5next/common/kda.py), [SP32-SRC-vllm-models-glm5next-common-model-py](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/models/glm5next/common/model.py), [SP32-PR-59147](https://api.github.com/repos/vllm-project/vllm/pulls/59147).

**DCP:** the compressed k-pool indexer gains DCP support. At fixed TP4/8, start target-only with DCP1/2/4 where divisible, using `--cp-kv-cache-interleave-size 4` for the checkpoint's pool factor4. DCP uses ranks within TP; it does not add GPUs or shard KDA and the short k-pool tail. Top-k merging and workspace grow; FlashInfer sparse MLA rejects combined PCP+DCP. The B300/NoPE-512 comparison requires the `FLASHINFER_MLA_SPARSE` path, supported BF16/plain FP8 cache and PCP1. `FLASHMLA_SPARSE` rejects this NoPE-512 geometry on capability major10. Check the resolved backend before comparing DCP. [SP32-SRC-vllm-v1-attention-backends-mla-flashmla_sparse-py](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/v1/attention/backends/mla/flashmla_sparse.py). Evaluate this separately from lowering state precision. [SP32-SRC-vllm-models-glm5next-nvidia-sparse_indexer-py](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/models/glm5next/nvidia/sparse_indexer.py), [SP32-SRC-vllm-v1-attention-backends-mla-indexer-py](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/v1/attention/backends/mla/indexer.py), [SP32-SRC-vllm-v1-attention-backends-mla-flashinfer_mla_sparse-py](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/v1/attention/backends/mla/flashinfer_mla_sparse.py).

Internal FlashKDA prefill checkpoints add a useful repeated-prefix comparison, with checkpoint memory and boundary correctness costs. ## Startup, restart and cache measurement under KServe

**Shared-memory arena: release-note contradiction.** The notes say it is enabled by default, but the pinned release sets `enable_shm_tensor_arena=False` and describes it as experimental opt-in. It applies only to eligible queues whose readers are all node-local. Eight 256 MiB slots reserve about 2 GiB of `/dev/shm` address space plus metadata per arena, with lazy physical population and a free-space check at initialization. Full slots or oversized tensors fall back to serialization. A KServe multimodal/TP experiment must account for the resolved flag, queue count, shared-memory volume and host-memory budget; this is not an unconditional new requirement for text-only TP1. [V032-R-PARALLEL](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/config/parallel.py), [V032-R-SHM-ARENA](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/distributed/device_communicators/shm_tensor_arena.py), [V032-R-SHM-BROADCAST](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/distributed/device_communicators/shm_broadcast.py).

**Host-side opportunities:** local tokenizer/processor snapshots can reduce repeated Hub lookups; the helper downloads non-weight files, bypasses local/ModelScope inputs and falls back to the original repository ID on failure. With multiple Python API workers, the new balancer uses best-effort open-connection counts within the frontend. This is distinct from KServe replica routing and GPU-load scheduling. Compare startup or CPU-bound short-request latency only where those paths are active; upstream small-model percentages do not establish catalog-model gains. [V032-R-REPO-UTILS](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/transformers_utils/repo_utils.py), [V032-R-API-LAUNCHER](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/entrypoints/launchers/launcher.py).

**Kernel preparation:** the new `vllm download-kernels` command delegates to the installed FlashInfer CLI. It downloads precompiled kernels where its CUDA lane provides them, otherwise installs the cubin wheel. Its `--dry-run` previews this action. Evaluate preparing the pinned image/cache before serving and measure cold readiness separately from warm-request latency. The command is not a model-specific speed setting. [V032-CLI-DOWNLOAD](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/entrypoints/cli/download_kernels.py), upstream PR #58765.

**Autotune preloading:** the release notes mention `--preload-autotune`, but the inspected release CLI/documentation run autotuning during `vllm preload` unless FlashInfer autotuning is disabled. Do not copy an absent flag from the summary. This moves work before engine startup; it does not remove the work. When a cacheable MTP/EAGLE/EAGLE3 draft has its own daemon group, both groups skip this preload tuning and the first engine fills the cache. Other draft methods are outside that skip predicate. [V032-PRELOAD-CLI](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/entrypoints/cli/preload.py), [V032-PRELOAD-DOC](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/docs/features/preload.md), [V032-WEIGHT-CACHE-UTILS](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/model_executor/model_loader/weight_cache/utils.py), upstream PR #60085.

A weight-cache daemon needs compatible post-processed weights, rank placement, local GPU IPC and socket access, plus a lifecycle that survives the engine restart. An ordinary KServe pod restart does not establish those conditions. Start with kernel/autotune cache preparation; investigate a surviving daemon only after inspecting the installed runtime integration. Measure model load, compilation, graphs, autotune and readiness independently. A full TP8 service still requires a drain/replace strategy on an eight-GPU node with no spare GPU capacity.

**Prefix attribution:** `vllm:prompt_tokens_cached_by_source_total` distinguishes local GPU, local CPU and external KV reuse. Use the labels actually exposed by the selected deployment. This helps explain a chat improvement without counting reused input as newly generated output or assuming a cache hit was local. Report generated output tokens, uncached prefill and reused prefix separately; account for routing and queueing at the KServe endpoint. [V032-METRICS-LOGGER](https://raw.githubusercontent.com/vllm-project/vllm/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/v1/metrics/loggers.py), upstream PR #56318.

## Small, discriminating comparisons

These are experiment designs for the separate execution repository. They do not add a benchmark harness or results to the atlas.

| Order | Comparison | What it establishes |
| --- | --- | --- |
| 1. Release control | v0.31 versus v0.32, same pinned export and explicit settings, target-only | End-to-end release effect, including dependencies; not attribution to one PR. Check serialized inputs, resolved kernels/cache, HBM and output/tool validity first. |
| 2. Unique prompts | Runtime warmed, semantic prefix cold; 1K/8K/32K inputs and short versus long outputs; concurrency 1 then 8 | Whether improvements affect prefill, decode or host overhead. Report TTFT, inter-token latency, output rate and completion time independently. |
| 3. Growing sessions | Stable system/tool prefix, increasing history, idle gaps, branches, cancellation; concurrency 8/32 within measured capacity | Recurrent/KV correctness, prefix reuse, evictions and p95 turn latency. Do not infer persistent conversation storage from prefix caching. |
| 4. Speculation | Target-only versus the exact supported draft at natural proposal depths; low and higher concurrency | Accepted length, proposal/verification cost, extra HBM and whole-request gain. Use language/code prompts and fixed reasoning/sampling; synthetic acceptance is not a production result. |
| 5. Topology and precision | One wider group versus independent narrower KServe groups, fixed total GPU budget; weight precision and KV precision separately | Whether latency, capacity or node goodput justifies the communication/replica tradeoff. Keep EP world size and deployment replica count distinct. |
| 6. Coding episodes and restart | Fixed tool harness/tasks plus cold/warm KServe lifecycle observations | Successful tasks per node-hour with a quality floor, parser correctness and recovery time. Traffic replay alone does not establish coding success. |

Retain configurations that improve the intended metric without unacceptable quality, memory or tail-latency changes. A useful release comparison can show a correctness or capacity gain with no token-rate gain. Recheck interactions for finalists, especially speculation × prefix reuse × quantization × concurrency; sequential tuning does not prove a global optimum.
