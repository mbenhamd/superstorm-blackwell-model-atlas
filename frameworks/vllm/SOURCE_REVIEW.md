## What the launch knobs mean in v0.31.0

The following are **released-source semantics**, checked at `db9527a46873454610df6dbedf79a36d6bf1a7f6`. The main snapshot `fa75d345…` was checked separately for the same argument/configuration paths. Defaults are starting behavior; the atlas's explicit values are unmeasured experiment choices.

| Setting | Verified meaning | Practical consequence |
| --- | --- | --- |
| `--gpu-memory-utilization 0.88` | Default is **0.92**. `--device-memory-utilization` is an alias to the same argument. Requested executor memory is `ceil(device_total_bytes × utilization)` for each worker; startup rejects insufficient free memory | 0.88 leaves a nominal 12% outside the executor's automatic budget. Weights, profiled non-KV allocations and applied graph-memory estimates are deducted before KV sizing. It is neither 88% KV allocation nor a hard process-memory quota |
| `--kv-cache-memory-bytes` | A nonzero explicit byte budget bypasses automatic fraction-based KV sizing | A utilization sweep is not a cache-budget sweep while this override is active; startup and runtime allocations still need headroom |
| `--kv-cache-dtype auto` / `fp8` | `auto` first consults supported ModelOpt KV metadata, then downstream dtype/model/backend resolution. Ordinary fallback is model dtype. CUDA `fp8` denotes E4M3; it does not quantize model weights or recurrent state | Record actual cache-group dtypes and scaling. A weight export labeled FP8 does not prove FP8 KV, and `auto` does not universally mean BF16. Special compressed caches and skipped layers require their own accounting |
| Prefix caching | Generative models normally resolve it on when their model capability supports it; the bare cache-config default is true | It saves repeated prefill work only for matching prefixes with valid state. It does not eliminate work for new tokens. Hybrid state, eviction and restored-prefix correctness remain gates |
| Chunked prefill | Generative models normally resolve it on when supported. `max_num_batched_tokens` is a scheduler-step token budget, not total context or total cache capacity | Larger chunks may improve prefill efficiency while delaying decode. Explicitly record the resolved budget and admission limits; hardware-dependent defaults are not a workload recommendation |
| `--async-scheduling` | Default input is `None`; configuration normally enables it when compatible. Explicit true rejects listed incompatible speculative modes, unpadded draft batches or unsupported executors; auto mode can disable it | Compare against explicit `--no-async-scheduling` only after checking the resolved runner and executor. An accepted flag alone does not prove that the desired overlap path is used |

[RR-ENG-V-STABLE-CACHE-PIN](https://raw.githubusercontent.com/vllm-project/vllm/db9527a46873454610df6dbedf79a36d6bf1a7f6/vllm/config/cache.py), [RR-ENG-V-STABLE-ARG_UTILS-PIN](https://raw.githubusercontent.com/vllm-project/vllm/db9527a46873454610df6dbedf79a36d6bf1a7f6/vllm/engine/arg_utils.py), [RR-ENG-V-STABLE-UTILS](https://raw.githubusercontent.com/vllm-project/vllm/db9527a46873454610df6dbedf79a36d6bf1a7f6/vllm/v1/worker/utils.py), [RR-ENG-V-STABLE-GPU_WORKER-PIN](https://raw.githubusercontent.com/vllm-project/vllm/db9527a46873454610df6dbedf79a36d6bf1a7f6/vllm/v1/worker/gpu_worker.py), [RR-ENG-V-STABLE-TORCHUTILS](https://raw.githubusercontent.com/vllm-project/vllm/db9527a46873454610df6dbedf79a36d6bf1a7f6/vllm/utils/torch_utils.py).

[ATTV-REL](https://api.github.com/repos/vllm-project/vllm/releases/latest), [ATTV-TAG](https://api.github.com/repos/vllm-project/vllm/git/ref/tags/v0.31.0), [ATTV-MAIN](https://api.github.com/repos/vllm-project/vllm/commits/main).

### Selection is conditional, not a universal ranking

The CUDA selector builds a priority list, then validates architecture, activation/cache dtype, head size, block size and requested features. The first valid candidate wins. An explicitly selected **invalid backend raises an error**; the generic selector does not silently substitute another backend. Version selection *inside* `FLASH_ATTN` has separate fallback rules. Model-owned attention layers, described below, can bypass this generic selector. [ATTV-S-CUDA](https://raw.githubusercontent.com/vllm-project/vllm/db9527a46873454610df6dbedf79a36d6bf1a7f6/vllm/platforms/cuda.py), [ATTV-M-CUDA](https://raw.githubusercontent.com/vllm-project/vllm/07f3857fb93772fed64e06642cdb0b8c03e0b249/vllm/platforms/cuda.py), [ATTV-S-BASE](https://raw.githubusercontent.com/vllm-project/vllm/db9527a46873454610df6dbedf79a36d6bf1a7f6/vllm/v1/attention/backend.py).

| Eligible path | v0.31.0 priority / behavior | Selected main difference |
| --- | --- | --- |
| Ordinary causal, non-MLA attention on SM100/SM103 | `FLASHINFER` before `FLASH_ATTN`; multimodal-prefix requests first consider `TRITON_FLASHINFER` | Same ordering |
| Non-causal, non-MLA attention on SM100/SM103 | `FLASH_ATTN` before `FLASHINFER` | Same ordering |
| Ordinary non-MLA attention on SM120 | `FLASH_ATTN` before `FLASHINFER`; vLLM's FA4 availability gate excludes SM120, so an eligible FlashAttention path normally resolves FA2 | Same gate and ordering; standalone FA4's hardware support does not change this wrapper |
| Sparse MLA on SM100/SM103 | Quantized cache prefers `FLASHINFER_MLA_SPARSE` before `FLASHMLA_SPARSE`; BF16 reverses these above 16 local query heads | Adds `FLASH_ATTN_MLA_SPARSE_FA4` first for unquantized cache with at most 16 local query heads, subject to its own restrictions |
| MLA on SM120 | Considers `TRITON_MLA` and `FLASHINFER_MLA_SPARSE_SM120`, whose dense/sparse capability checks differ | Same architecture distinction |

The FA4 selector fragment below is checked against both configuration schemas. It applies only after the exact model, cache and attention path qualify. `flash_attn_version` is the **configuration field**; `fa_version` is an internal kernel-call argument and is not the field to put in this JSON. This is a parser reference, not a complete launch recipe. [ATTV-S-CONFIG](https://raw.githubusercontent.com/vllm-project/vllm/db9527a46873454610df6dbedf79a36d6bf1a7f6/vllm/config/attention.py), [ATTV-M-CONFIG](https://raw.githubusercontent.com/vllm-project/vllm/07f3857fb93772fed64e06642cdb0b8c03e0b249/vllm/config/attention.py), [ATTV-S-ARGS](https://raw.githubusercontent.com/vllm-project/vllm/db9527a46873454610df6dbedf79a36d6bf1a7f6/vllm/engine/arg_utils.py).

```text
--attention-backend FLASH_ATTN --attention-config '{"flash_attn_version":4}'
```

On the checked CUDA paths, FA3 normally serves Hopper and FA4 is preferred inside `FLASH_ATTN` on the SM100 family when available. Even an explicit FA4 version request can resolve FA2 for ALiBi, batch-invariant mode or unsupported head/feature combinations. For Blackwell, the resolver retains eligible dimensions up to 128, the dedicated 256/256 QK/V route, and the 192/128 Diff-KV route; other larger dimensions fall back. The dedicated 256 route requires 128-token kernel pages and excludes quantized KV, sinks, soft capping, bidirectional multimodal prefixes, R-SWA and decode context parallelism. A passing broad head-size check is therefore insufficient to conclude that FA4 executes. [ATTV-S-FA-UTIL](https://raw.githubusercontent.com/vllm-project/vllm/db9527a46873454610df6dbedf79a36d6bf1a7f6/vllm/v1/attention/backends/fa_utils.py), [ATTV-M-FA-UTIL](https://raw.githubusercontent.com/vllm-project/vllm/07f3857fb93772fed64e06642cdb0b8c03e0b249/vllm/v1/attention/backends/fa_utils.py).

The generic `FLASH_ATTN` backend declares FP16/BF16 activation support and ordinary FP16/BF16 or eligible E4M3 FP8 KV support; it does **not** advertise NVFP4 KV. FA4 paged attention is wired through `block_table → page_table`; multimodal-prefix and R-SWA masks use `mask_mod`. Although its low-level wrapper accepts block-sparse tensors, the generic backend remains non-MLA/non-sparse in the registry's capability checks. Its sparse kernel API is not a universal switch that supplies an indexer to any checkpoint. [ATTV-S-FA](https://raw.githubusercontent.com/vllm-project/vllm/db9527a46873454610df6dbedf79a36d6bf1a7f6/vllm/v1/attention/backends/flash_attn.py), [ATTV-M-FA](https://raw.githubusercontent.com/vllm-project/vllm/07f3857fb93772fed64e06642cdb0b8c03e0b249/vllm/v1/attention/backends/flash_attn.py), [ATTV-S-FA-API](https://raw.githubusercontent.com/vllm-project/vllm/db9527a46873454610df6dbedf79a36d6bf1a7f6/vllm/vllm_flash_attn/flash_attn_interface.py).

### FP8 weights, cache and attention arithmetic

An FP8 checkpoint, FP8 KV storage and FP8 attention matrix products are separate choices. Weight quantization selects compatible linear/MoE implementations; it does not by itself select the Q/K/V operand types. Conversely, eligible FP8 KV **does trigger FP8 attention** on the generic FA4 path below, even though the model's activation configuration is BF16.

| Resolved generic FA4 path | Source-traced arithmetic and output | Eligibility boundary |
| --- | --- | --- |
| SM100/SM103 family, BF16 activations and `fp8` / `fp8_e4m3` KV | The attention layer quantizes Q with `_q_scale`; the backend views cached K/V as FP8 and passes FP32 `q_descale`, `k_descale`, `v_descale` shaped `(batch, KV heads)`. The vendored SM100 kernel uses FP8 operands for QK and PV, with FP32 accumulators and BF16 output | Requires FA4 to survive the earlier head/feature checks. The checked path excludes E5M2 cache, the quantized `head_size=256` route, generic MLA/DSA and NVFP4 cache. This is ordinary E4M3 FP8, not evidence of MXFP8 block scaling |
| SM90's eligible `head_size=512` FA4 FP8-cache path | Q remains FP16/BF16 at the engine boundary. The wrapper passes `fp8_kv_dequant=True` and no Q descale; the kernel dequantizes K/V and narrows BF16 Q to **FP16 computation**, then writes native FP16/BF16 output | FP8 cache storage here does not imply FP8 matrix products; other Hopper configurations can resolve a different FA version |

The Hopper kernel explicitly asserts FP16 computation for this dequantization path while allowing FP16/BF16 Q and final output. [FP8V-S-FORK-SM90](https://raw.githubusercontent.com/vllm-project/flash-attention/9cd61de38763d712bb6ce56e2a02cc2bf718c89f/flash_attn/cute/flash_fwd_sm90.py).

The conversion and descale forwarding are present in both inspected snapshots. [FP8V-S-ATTENTION](https://raw.githubusercontent.com/vllm-project/vllm/db9527a46873454610df6dbedf79a36d6bf1a7f6/vllm/model_executor/layers/attention/attention.py), [FP8V-S-FA](https://raw.githubusercontent.com/vllm-project/vllm/db9527a46873454610df6dbedf79a36d6bf1a7f6/vllm/v1/attention/backends/flash_attn.py), [FP8V-M-FA](https://raw.githubusercontent.com/vllm-project/vllm/07f3857fb93772fed64e06642cdb0b8c03e0b249/vllm/v1/attention/backends/flash_attn.py), [FP8V-S-FA-API](https://raw.githubusercontent.com/vllm-project/vllm/db9527a46873454610df6dbedf79a36d6bf1a7f6/vllm/vllm_flash_attn/flash_attn_interface.py), [FP8V-M-FA-API](https://raw.githubusercontent.com/vllm-project/vllm/07f3857fb93772fed64e06642cdb0b8c03e0b249/vllm/vllm_flash_attn/flash_attn_interface.py).

The fork's FP8 output check requires BF16 even when the caller supplies `out`; vLLM preserves the original activation dtype when allocating that output. Therefore the backend's broad FP16/BF16 declaration does not establish FP16-activation compatibility for this native FP8 route. Kernel arithmetic and narrower dtype/architecture gates: [FP8V-S-FORK-API](https://raw.githubusercontent.com/vllm-project/flash-attention/9cd61de38763d712bb6ce56e2a02cc2bf718c89f/flash_attn/cute/interface.py), [FP8V-M-FORK-API](https://raw.githubusercontent.com/vllm-project/flash-attention/b273a02621d3c94bc747df67204f591b67f38fae/flash_attn/cute/interface.py), [FP8V-S-FORK-SM100](https://raw.githubusercontent.com/vllm-project/flash-attention/9cd61de38763d712bb6ce56e2a02cc2bf718c89f/flash_attn/cute/flash_fwd_sm100.py), [FP8V-S-FA-UTIL](https://raw.githubusercontent.com/vllm-project/vllm/db9527a46873454610df6dbedf79a36d6bf1a7f6/vllm/v1/attention/backends/fa_utils.py).

### Sparse support belongs to a model and an implementation

| Path | What the inspected implementation actually does | Boundary |
| --- | --- | --- |
| DeepSeek V3.2-style DSA | `index_topk` enables an indexer; it scores candidate token positions and writes per-query top-k token indices | MLA by itself does not enable this branch. A page holding those tokens is storage, not necessarily a scored block summary |

### NVFP4 weights and NVFP4 cache are independent choices

An eligible NVFP4 weight export may use a different precision for attention inputs and cache. The dense/GQA cache stores separate K/V head slots; MLA stores model-specific latent/positional records; recurrent blocks retain their own state. Neither an NVFP4 filename nor selecting FA4 establishes which of these allocations became four-bit. See [precision and kernels](../../reports/precision-and-kernels.md) and [memory accounting](../../reports/memory-math.md).

| Cache path | Released v0.31.0 | Selected main |
| --- | --- | --- |
| Generic non-MLA `nvfp4` / `nvfp4_4over6` | FlashInfer requires SM100-family TRTLLM availability for both prefill and decode. K/V head sizes must be symmetric. Both variants share the read layout; `4over6` changes scale selection while storing | Retains that SM100 path. Adds plain `nvfp4` on SM80/90/120 via FlashInfer's FA2 path, with eligible XQA decode on SM120. The added path rejects `nvfp4_4over6`, head size 64, sinks and DCP; non-causal NVFP4 attention is also rejected |
| DSA `nvfp4_ds_mla` | `FLASHMLA_SPARSE`, SM100 family, DeepSeek V3.2 geometry: 512 packed NoPE values, 64 FP8 RoPE values and 32 block scales, **352 bytes/token** | Retains this distinct format and geometry; it is not generic `nvfp4` GQA storage or the main FA4 sparse backend's BF16 cache |
| DeepSeek V4.1 compressed NVFP4 cache | `FLASHMLA_MEGA_ATTN_DSV41` has a separate 288-byte compressed record, with FP8 sliding-window cache and topology/kernel availability gates | Remains model-specific; selected main routes V4.1 PCP to FlashMLA sparse attention instead |

## Cache, graphs, distribution and restart

Prefix reuse has to preserve each participating cache/state group. A recurrent checkpoint represents a particular processed prefix; sharing attention blocks without the matching recurrent state is insufficient. v0.31.0 renamed the shared-checkpoint option to `--enable-mamba-shared-prefix-checkpoint`. The hybrid-manager design page explicitly describes an older source basis, so use it for the mechanism and inspect the selected engine for current grouping/support. Cache-boundary behavior determines whether reused state is valid. [VEXP-REL](https://github.com/vllm-project/vllm/releases/tag/v0.31.0) [VEXP-HYBRID](https://docs.vllm.ai/en/latest/design/hybrid_kv_cache_manager/)

CUDA graphs reuse captured GPU work to reduce launch overhead. Graph selection depends on batch shape and backend support; the requested mode can be downgraded. More capture shapes can require more memory and initialization time. Record the **resolved** mode and replay path. `--enforce-eager` also disables JIT warmup in v0.31.0, so comparing that switch alone does not isolate graph replay. A graph-only comparison must hold compilation and warmup fixed. [VEXP-GRAPH](https://docs.vllm.ai/en/latest/design/cuda_graphs/) [VEXP-REL](https://github.com/vllm-project/vllm/releases/tag/v0.31.0)

Expert parallelism distributes experts across the TP×DP ranks while attention uses its own replication/sharding pattern. Its communication and kernel backend must match the actual node and dependencies. Prefill/decode separation instead assigns phases to different engines and transfers state; it can help tail latency while introducing transfer and duplicated-residency costs. These are separate decisions. Compare whole-node allocations before asking whether a 4+4 split earns its overhead. [VEXP-EP](https://docs.vllm.ai/en/latest/serving/expert_parallel_deployment/) [VEXP-PD](https://docs.vllm.ai/en/latest/features/disagg_prefill/)

The weight-cache daemon retains post-processed GPU weights and exposes them through local IPC. Matching fingerprints, quantization support and a surviving daemon are required; a mismatch can fall back to disk loading. This reduces one part of a restart, while compilation, graph capture and service readiness still need timing. Initialized-engine snapshots are a different experimental mechanism: current documentation limits them to one GPU/TP1, no speculation, the same host/software environment, and reports validation only for dense FP16. Neither mechanism establishes that an eight-GPU KServe service can restore all request state. [VEXP-PRELOAD](https://docs.vllm.ai/en/latest/features/preload/) [VEXP-SNAPSHOT](https://docs.vllm.ai/en/latest/features/initialized_snapshots/)

## Gemma and Kimi compatibility gates

Gemma 4 also needs attention-mode qualification. Released #53175 addresses FP8-KV backend selection for the exact `RedHatAI/gemma-4-31B-it-FP8-dynamic` export, including the 512-wide head path. Its report explains why a causal text backend cannot simply be forced onto bidirectional multimodal-prefix attention; the composite backend dispatches by request/layer requirements. Its H200 results do not determine the B300 backend or performance. Inspect resolved per-layer kernels and compare text, actual image-prefix requests and long-prefix reuse before treating FP8 KV as a capacity improvement. This establishes no compatibility claim for another Gemma derivative. [RR-ENG-V-PR53175](https://api.github.com/repos/vllm-project/vllm/pulls/53175), [RR-ENG-V-PR53175-DIFF](https://github.com/vllm-project/vllm/commit/4fb767ff0a0e0aae9dd2720c47245d0202136dfd.diff), [VEXP-REL](https://github.com/vllm-project/vllm/releases/tag/v0.31.0).

The October 17 review supersedes the earlier open-PR blocker rationale. Selected v0.31.0 source already contains Kimi mixed-precision KDA alignment, MLA dtype handling and related scaling fixes; historical PR #52406 does not establish their absence. The exact NVIDIA mixed-export image remains unqualified, and its old bundled patch imports classes removed by the release's ModelOpt refactor. See the [current precision/source analysis](../../companies/moonshot-ai/kimi-k3/precision.md) for the distinction between source availability and image compatibility.
