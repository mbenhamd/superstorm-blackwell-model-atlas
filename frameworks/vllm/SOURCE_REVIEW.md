## Recent changes, mechanism and limits

All eight PRs below were observed merged into main on **October 15, after the stable release**. Their immutable diffs and relevant current-source functions were inspected. The table separates upstream evidence from proposed B300 benefits.

| Change; merge commit | Mechanism and useful hypothesis | Scope and cost to check | Experiment |
| --- | --- | --- | --- |
| [#61044](https://github.com/vllm-project/vllm/pull/61044); `9cede34a674c392092134e34218b127d6bbb3679` | Create cuBLAS/cuBLASLt handles before memory pressure builds, reducing a startup-allocation failure path | The reported reproduction uses Gemma 3n on an H200 MIG slice. This is a reliability candidate for tight B300 budgets, with no B300 speed claim | V01, V10 |
| [#58737](https://github.com/vllm-project/vllm/pull/58737); `c825e1d235896694ca50160286440859ed46d7d3` | Fuse the align-mode recurrent-state block-table gather into one Triton launch | Shared utility used by several recurrent backends; verify the active model calls it. | [#61538](https://github.com/vllm-project/vllm/pull/61538); `4d58fa254a869a5d9d0aab250ab125503d3cef26` | Unify MegaMoE dispatch around explicit precision, activation and shared-expert combinations; add an NVFP4 kernel row | Existing DeepSeek/Kimi callers in the diff retain MXFP4. | [#58668](https://github.com/vllm-project/vllm/pull/58668); `d486219fc2f27a981d6eda53eb2b95bfde1a1d63` | Remove stop-trimmed speculative positions from computed-token accounting and resolve their async placeholders | A resumed streaming-input request must recompute its new tokens instead of reusing discarded draft KV. This concerns resumable input sessions; ordinary SSE output alone does not exercise it | V05 |
| [#61873](https://github.com/vllm-project/vllm/pull/61873); `54d9b1cb487c2a2f12506942820f0ae443807093` | Update FlashInfer sparse-MLA draft decode metadata in place, avoiding a broader rebuild between proposals | Enabled only with DCP=1, PCP=1 and no HiSparse. The author's small GLM 5.3 Blackwell benchmark is a reproduction lead, with no node-wide or high-load conclusion | V07 |
| [#61161](https://github.com/vllm-project/vllm/pull/61161); `9edcc7fa7ec858e13d4dc10ed968b741e2c95d6a` | Include speculative step in the random stream so revisited positions do not reuse draws conditioned on an earlier verification decision | Correctness fix for Model Runner V2 block verification and probabilistic drafting. Fixed-seed probabilistic strings can change across versions; target-distribution checks matter | V05 |

These changes address different bottlenecks. A faster metadata kernel helps only when that kernel is on the active path and material in the trace. A scheduler change matters when admission is constrained. A cheaper proposal head helps only if accepted output saves more target work than the extra drafting costs. These are hypotheses to measure, not additive speedup percentages.

## Cache, graphs, distribution and restart

Prefix reuse has to preserve each participating cache/state group. A recurrent checkpoint represents a particular processed prefix; sharing attention blocks without the matching recurrent state is insufficient. v0.31.0 renamed the shared-checkpoint option to `--enable-mamba-shared-prefix-checkpoint`. The hybrid-manager design page explicitly describes an older source basis, so use it for the mechanism and inspect the selected engine for current grouping/support. V03 stresses the boundaries where reused state becomes visible. [VEXP-REL](https://github.com/vllm-project/vllm/releases/tag/v0.31.0) [VEXP-HYBRID](https://docs.vllm.ai/en/latest/design/hybrid_kv_cache_manager/)

CUDA graphs reuse captured GPU work to reduce launch overhead. Graph selection depends on batch shape and backend support; the requested mode can be downgraded. More capture shapes can require more memory and initialization time. Record the **resolved** mode and replay path. `--enforce-eager` also disables JIT warmup in v0.31.0, so comparing that switch alone does not isolate graph replay. V04 keeps compilation and warmup fixed for its graph-only comparison. [VEXP-GRAPH](https://docs.vllm.ai/en/latest/design/cuda_graphs/) [VEXP-REL](https://github.com/vllm-project/vllm/releases/tag/v0.31.0)

Expert parallelism distributes experts across the TP×DP ranks while attention uses its own replication/sharding pattern. Its communication and kernel backend must match the actual node and dependencies. Prefill/decode separation instead assigns phases to different engines and transfers state; it can help tail latency while introducing transfer and duplicated-residency costs. These are separate decisions. V08 compares whole-node allocations, then V09 asks whether a 4+4 split earns its overhead. [VEXP-EP](https://docs.vllm.ai/en/latest/serving/expert_parallel_deployment/) [VEXP-PD](https://docs.vllm.ai/en/latest/features/disagg_prefill/)

The weight-cache daemon retains post-processed GPU weights and exposes them through local IPC. Matching fingerprints, quantization support and a surviving daemon are required; a mismatch can fall back to disk loading. This reduces one part of a restart, while compilation, graph capture and service readiness still need timing. Initialized-engine snapshots are a different experimental mechanism: current documentation limits them to one GPU/TP1, no speculation, the same host/software environment, and reports validation only for dense FP16. Neither mechanism establishes that an eight-GPU KServe service can restore all request state. [VEXP-PRELOAD](https://docs.vllm.ai/en/latest/features/preload/) [VEXP-SNAPSHOT](https://docs.vllm.ai/en/latest/features/initialized_snapshots/)

## Kimi compatibility remains a separate gate

Fresh retrieval still shows **#52406 open**. It handles ModelOpt FP8-block projection padding/trimming and MLA scale absorption for Kimi attention. Its author separates unit/static validation of that branch from an eight-B300 evaluation using equivalent compatibility logic. The newly merged MegaMoE work does not resolve this attention-layout issue. [VEXP-52406](https://github.com/vllm-project/vllm/pull/52406)

NVIDIA's pinned Kimi NVFP4 card documents a patched vLLM container and bundled runtime patches. Preserve that as a distinct artifact candidate. An unmodified stable image, a main build and the publisher's patched image need separate identities and load/quality gates. [kimi-k3-NV](https://huggingface.co/nvidia/Kimi-K3-NVFP4/blob/b2428a0b83a8b712ff2e1a8448a103d4175341f1/README.md)

Before adopting any candidate, trace model resolution → weight loader → quantization/backend dispatch → scheduler/cache → draft verification → output parser. The [experiment plan](EXPERIMENTS.md) specifies the controls and failure cases. No independent end-to-end B300 reproduction was established by this source review.
